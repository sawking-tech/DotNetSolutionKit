# Стиль кода в решении

Генерируется с `--code-style`, по умолчанию выключен. Передаётся с `--solution`.

В решении один файл правил стиля - `.editorconfig` в корне. Флаг кладёт туда правила самого шаблона, все
в `suggestion`, и с этого момента файл командин: она его правит, поднимает то, что хочет удерживать, и
добавляет свои правила. `dotskit` читает этот файл, чтобы разложить код, который приносит обновление, - и
код приезжает в том стиле, в котором команда уже пишет.

## Зачем файл, а не настройка форматтера

Обновление пишет файлы, которых команда никогда не видела: модуль переехал в другой проект, контракт
получил поле, тест поехал за своей возможностью. Написанные в стиле шаблона - четыре пробела, скобка на
своей строке, `using` вне пространства имён - они смешивают в одном проекте две раскладки и превращают
каждый мерж в конфликт про пробелы.

Файл решает это один раз. Команда называет свой стиль там, где его уже читают все редакторы .NET и
`dotnet format`, и тулзе есть по чему разложить приходящий код. Без файла тулзе нечего соблюдать, и она
оставляет байты шаблона как есть.

`.editorconfig` читают и редакторы, и SDK, поэтому файл служит команде и вне обновления: IDE форматирует
по нему новый код, а правило, поднятое до `warning`, валит их сборку на нарушении.

## Что кладёт флаг

`template/.editorconfig.template` - правила собственного репозитория шаблона, каждое в `suggestion`.
`suggestion` говорит, что это за файл: отправная точка. Сборка команды не падает на наших правилах, пока
команда их не поднимет, а группы правил те же, что [у самого репозитория](../architecture/code-style.md), -
поэтому два файла не расходятся.

Правило в `suggestion` всё равно применяется тулзой при обновлении. Строгость говорит, что с нашим стилем
делает сборка команды; она не значит, что команда хочет другую раскладку.

## Мерж и форматирование при обновлении

Мерж трёхсторонний: выход шаблона, с которого решение генерировалось, решение в том виде, в каком его
держит команда, и выход шаблона, к которому оно идёт. Стиль входит до мержа, и только на стороне шаблона.

1. **Обе стороны шаблона раскладываются по правилам команды.** Выход, с которого решение пришло, и выход,
   к которому оно идёт, каждый в своей копии, форматируются объединением двух файлов: правила шаблона,
   затем правила команды, так что правило команды главнее там, где названы оба. Файлы решения не пишутся.
2. **Почему обе, а не только новая.** git сравнивает каждую сторону с базой. База, оставленная в стиле
   шаблона, против команды, которая переформатировала каждую строку, читается как каждая строка, изменённая
   командой, - и мерж сообщает конфликт на каждой. Разложенные с обеих сторон, они совпадают по стилю и
   расходятся только тем, что шаблон действительно изменил.
3. **Форматтер проходит дважды.** `dotnet format whitespace` применяет раскладку - скобки, отступы,
   пробелы. `dotnet format style --severity info` применяет правила кода, которые раскладка не трогает, -
   `using`, пространство имён, пустые строки. Ни один проход не заменяет другой; один проход оставляет
   половину стиля в форме шаблона.
4. **Объединение лежит рядом с файлом команды, не поверх него.** Оно пишется как `dotskit.editorconfig`
   рядом с собственным `.editorconfig` выхода и удаляется после прогона: файл, которого ждёт мерж, не
   должен исчезнуть, а файл команды - её.
5. **Правило в `none` остаётся выключенным.** Форматтеру передаётся `--severity info` - порог, при котором
   применяется правило в `suggestion`. Правило, выключенное командой в её файле, остаётся выключенным.

Форматируются только файлы, которые изменили обе стороны. Файл, который трогала одна команда, - её, и мерж
его не пишет.

## Решение со своим файлом

Решение, у которого есть `.editorconfig`, сохраняет его. Флаг - для решения без файла; обновление ничего
не добавляет в уже существующий файл, и форматирование идёт по правилам команды.

## Чего это стоит

- Мерж запускает `dotnet format` до четырёх раз: два прохода для выхода, с которого решение пришло, и два
  для того, к которому идёт. На большом решении это самая медленная часть обновления, и поэтому
  форматируются файлы, изменённые обеими сторонами, а не всё дерево.
- Тулза форматирует копию и мержит её. Файлы решения обновление не раскладывает; файл, чья раскладка
  команде не нравится, по-прежнему форматирует команда.
- Стиль следует правилам, которые называет файл. Правило, добавленное командой, которого не знает
  установленный SDK, форматтер сообщает и пропускает.
