# ADR-007: единый стиль кода, за который отвечают форматтеры

**Статус:** принято, 2026-10-29

**Автор:** Владимир Савкин, создатель DotNetSolutionKit

## Контекст

Большую часть кода репозитория генерирует ИИ-модель как инструмент, как описано в
[Работе с ИИ-агентами](../getting-started/working-with-ai-agents.ru.md): автор принимает решения, задаёт архитектуру
и правила, модель генерирует код, автор проверяет результат и отвечает за него. До 2.9 стиль этого кода держался
только на словах CLAUDE.md. Вероятностный генератор по своей природе не гарантирует, что результат соблюдает правила, записанные
словами. Форматтер гарантирует, добавить его дёшево, и результат у него детерминированный, а это нужно и
обновлению. CI собирал с `-warnaserror` и больше ничего не проверял. В исходниках шаблона были вперемешку BOM, файлы без перевода строки в
конце и пробелы в конце строк, и сгенерированное решение получало их как есть: `dotnet new` копирует байты
исходного файла.

Стиль шаблона доходит и до команд. Команда обновляет решение через `dotskit upgrade`, и тот сливает изменения
шаблона с изменениями команды. Смена стиля в файле, который команда тоже правила, - это изменение строк, и слияние
показывает его конфликтом там, где никто не менял, что делает код. Первый же прогон CI этого решения это показал:
шаблон добавил перевод строки в конце `Program.cs`, тест дописал туда строку команды, и git сообщил о конфликте.

## Решение

За стиль отвечают форматтеры. Что они делают, то и стиль; ради стиля никто не правит файл руками, ни в
dotskit.template, ни в dotskit.tool. Человек меняет логику, и новая логика с первой строки пишется в стиле, чтобы
форматтерам было нечего менять.

Правила лежат в одном `.editorconfig` в корне репозитория. Он вне `template/`, поэтому пакет, который собирается из
`template/`, и сгенерированное решение его не несут; решение получит стиль только своим флагом, по умолчанию
выключенным (в плане, см. ниже).

Правила лежат в двух слоях.

- Правила, которые применяют форматтеры: байты каждого файла (UTF-8, LF, перевод строки в конце, без пробелов в
  конце строк, BOM только у файла решения), раскладка C#, скобки вокруг каждого тела, порядок using, пустые строки.
  Они на уровне `warning`: сборка с `-warnaserror` на них падает, а форматтер исправляет их без человека.
- Правила, которые не применяет ни один форматтер: имена, выражения коллекций, using-объявление, первичные
  конструкторы. Такое правило никогда не выше `suggestion`: IDE его предлагает, сборка на нём не падает, и ради него
  никто не переписывает код.

XML-документация (CS1573) и правила качества (CA) - не стиль: они о том, что код говорит и делает, и в
инструменте остаются на уровне `warning`.

Стиль файлов шаблона меняется только пакетом инструментов: `scripts/check-style.py --fix` для байтов и
`dotnet format` с корневым `.editorconfig`. Версия шаблона по стилю - это пакет, применённый к предыдущей версии,
поэтому `dotskit upgrade` может применить тот же пакет к стороне команды, и смена стиля ни с чем не сталкивается.
Первая часть уже на месте: оба слияния `dotskit` приводят три стороны файла к байтам стиля до слияния.

## Откуда правила

Правила следуют мейнстриму каждого языка и взяты из его источников, а не по памяти.

| Область | Источники |
|---|---|
| C# | [C# coding conventions](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/coding-style/coding-conventions), `.editorconfig` [dotnet/runtime](https://github.com/dotnet/runtime/blob/main/.editorconfig) и [dotnet/roslyn](https://github.com/dotnet/roslyn/blob/main/.editorconfig), [StyleCop.Analyzers](https://github.com/DotNetAnalyzers/StyleCopAnalyzers), умолчания JetBrains Rider и ReSharper |
| Как инструменты связаны | [Code analysis in .NET](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview), [опции правил стиля](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/code-style-rule-options), [dotnet format](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-format) |
| Python | [PEP 8](https://peps.python.org/pep-0008/) |
| Shell | [ShellCheck](https://github.com/koalaman/shellcheck) |
| JSON | [ADR-006](006-json-metadata-key-convention.ru.md), ключи метаданных |

С Microsoft правила совпадают в скобках Allman, using вне namespace с `System` первым, file-scoped namespace,
ключевых словах языка вместо имён типов платформы и одной инструкции на строку. Расходятся в трёх местах, и в
каждом указано, кто стоит на другой стороне:

| Правило | Microsoft | У нас | Вместе с |
|---|---|---|---|
| Поле `private static readonly` | `s_camelCase` | `PascalCase` | StyleCop SA1311 (а SA1308 запрещает `s_`), умолчания JetBrains |
| `var` | когда тип очевиден | на выбор автора | dotnet/runtime: разрешает `var` и не требует |
| Скобки | dotnet/runtime: можно опустить, когда каждый блок инструкции в одну строку | всегда | причина ниже |

Скобки стоят вокруг тела каждого `if`, `else`, `for`, `foreach`, `while`, `using` и `lock`: область тела видна
сразу и никогда не угадывается по отступу. По той же причине IDE не предлагает превращать блок `using` в
using-объявление, конец которого не виден ни в одной строке; объявления, которые уже есть в коде, остаются: ни один
форматтер не превращает их обратно. File-scoped namespace остаётся: его область - файл.

[Стиль кода](../architecture/code-style.ru.md) даёт каждое правило со значением и причиной.

## Рассмотренные варианты

- StyleCop.Analyzers пакетом. Большинство его правил повторяют правила IDE; его умолчания (`this.`, using внутри
  namespace) противоречат остальным источникам; без исключений он даёт 1 357 замечаний в инструменте. Четыре его
  правила, которые нам нужны (SA1505, SA1506, SA1508, SA1517: пустые строки у скобки, после XML-доки или в начале
  файла), - построчные шаблоны, их удержит проверка текста на каждом файле, исходники шаблона тоже.
- Префикс `s_`, как Microsoft пишет свой код. Его поддерживают только источники Microsoft, а это один автор.
- `global.json`, фиксирующий SDK на 8.0, чтобы правила были одинаковы на любой машине. Тесты инструмента генерируют
  решения вне репозитория; новый SDK собирает их там, наследует MSBuild от SDK 8, на котором идут тесты, и падает.
  Вместо этого `AnalysisLevel` 8.0 держит правила качества .NET 8, без такой цены.
- Правила, которые применяет человек: явные конструкторы или using-блоки по всему коду. Каждое - правка многих
  файлов руками, правка файлов шаблона, которую ни один инструмент не повторит на копии команды, а для первичных
  конструкторов это 117 классов шаблона, которые команда правит чаще всего.

## Цена

Раскладка принимается такой, какую дал форматтер, даже там, где человек разложил бы лучше, и не держится ни одно
вкусовое правило, которое форматтер не применяет. Взамен смену стиля между двумя версиями шаблона делает инструмент
и может повторить инструмент, поэтому обновление у команды идёт глаже и ломается реже.

## В плане

Следуют из этого решения и ещё не сделаны:

- хук pre-commit, который применяет байты и раскладку к файлам коммита;
- четыре построчных шаблона StyleCop в `check-style.py`;
- `dotnet format` на решениях, которые генерирует CI, и исходники шаблона, приведённые к нему пакетом;
- `dotskit upgrade`, применяющий весь пакет, байты и `dotnet format`, к сторонам слияния, а поверх -
  собственный `.editorconfig` команды;
- флаг, который даёт решению этот `.editorconfig` на уровне `suggestion`.
