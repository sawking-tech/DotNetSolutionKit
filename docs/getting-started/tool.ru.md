# dotskit

`dotskit` - инструмент командной строки DotNetSolutionKit. Он генерирует решение шаблоном, добавляет в него
сервисы, а сервисам - флаги, и сохраняет правки команды: если команда и шаблон изменили один файл, он
сливает изменения так же, как git сливает ветки.

Шаблон работает и без инструмента, см. [генерацию решения](template.ru.md). Инструмент делает
то, чего один запуск `dotnet new` не может: добавляет флаг сервису, папка которого уже есть, обновляет файл,
который команда изменила, и записывает в решение, из чего оно сгенерировано.

## Установка

```bash
dotnet tool install -g SawKing.DotsKit.Tool
```

Инструмент публикуется с версии 2.8. dotskit X.Y.Z генерирует шаблоном X.Y.Z: он ставит пакет
`SawKing.DotNetSolutionKit` своей версии в отдельное хранилище шаблонов и не трогает шаблон, установленный
через `dotnet new install`.

## Команды

```bash
# в пустой папке: решение с первым сервисом
dotskit new -N MyCompany -P MyProduct -S Orders

# в решении: ещё один сервис, с именами, базой и развёртыванием решения
dotskit new -S Billing --Storage true

# в решении: флаг для существующего сервиса
dotskit new -S Orders --MongoDB true

# в решении, созданном без dotskit: описать его в манифесте
dotskit init

# в решении: привести его к версии шаблона, которой соответствует инструмент
dotskit upgrade
```

`dotskit new` по папке решает, создать решение или добавить в него: ищет `src/services/*.All.sln` в папке
и выше. `--Solution` не нужен и ничего не меняет.

Параметры шаблона передаются как есть, в короткой или длинной форме, в любом регистре: `-S`, `--Storage`,
`--storage`, `--api-gateway`. См. [параметры](template.ru.md#параметры).

## Шаги команды

1. Проверяет папку. Новое решение создаётся в пустой папке или рядом с файлами в чистом рабочем дереве git.
   Для добавления в решение нужен `.dotskit/manifest.json` версии инструмента и чистое рабочее дерево. В решении
   работает одна команда за раз: вторая, запущенная, пока первая работает, говорит об этом и ничего не меняет;
   блокировка уходит вместе с процессом, который её держит, даже если его убили.
2. Генерирует во временной папке то, что шаблон даёт для решения до команды (базу) и после неё.
3. Пофайлово сравнивает базу, новый вывод шаблона и решение и показывает план: каждый файл с тем, что с ним
   будет и почему, и проекты, которые добавятся в `All.sln` или уйдут из него.
4. Спрашивает перед записью. `--yes` пишет без вопроса. Дерево, чистое на старте, пишется, только пока оно чистое
   на том же коммите; при `--allow-dirty` - только пока его файлы те же, что команда застала. Файл, сохранённый,
   или коммит, сделанный, пока строится план или ждёт ответа, останавливают запись, и ничего не пишется.
5. Пишет файлы. Новое содержимое сначала ложится рядом с файлом, потом файлы подменяются, а оригиналы
   откладываются в сторону. Ошибка или Ctrl+C до конца записи возвращают оригиналы; файл, который диск не дал
   вернуть, назван в ошибке, и его оригинал лежит рядом как `*.dotskit-old`, а новый файл, который диск не дал
   удалить, назван, чтобы его удалили. В слиянии через git остальное возвращает git, [ниже](#слияние-через-git).
   После записи оригинал, который диск не дал удалить (его держит другой процесс), остаётся рядом с файлом. Если
   процесс убит во время записи, рядом с файлами решения остаются `*.dotskit-new` и `*.dotskit-old`.
   `git status` показывает оставшееся, и следующая команда откажется работать с нечистым деревом, пока его не
   уберут через git.
6. Собирает `All.sln`.

Что происходит с файлом:

| В плане | Когда | Что записывается |
|---|---|---|
| `Add` | шаблон добавляет файл, которого в решении нет | файл шаблона |
| `Update` | команда файл не меняла | новый файл шаблона с окончаниями строк файла решения |
| `Merge` | файл изменили обе стороны, в строках порознь | обе правки |
| `Delete` | шаблон удалил файл, который команда не меняла | файл удаляется |
| `Kept` | одна сторона удалила файл, а другая изменила, или обе изменили двоичный файл | ничего: файл решения остаётся |
| `Conflict` | обе стороны изменили одни и те же строки или соседние | файл с обеими версиями: `<<<<<<< solution`, `=======`, `>>>>>>> template`; с `--conflict-style zdiff3` - ещё и база между ними, `||||||| base` |

Файл решения, который игнорирует его git, в том числе локальный `appsettings.Secrets.json`, не пишется. Новый файл шаблона, который git решения игнорировал бы, как файл секретов нового сервиса, пишется рядом со слиянием, а ручной `git merge --abort` его
оставляет: git о нём не знает. Закоммиченная символическая ссылка переносится как ссылка и не читается, как
двоичный файл, а путь, который через папку-ссылку ведёт за пределы решения, отклоняется до записи: то, куда
указывает ссылка, не попадает в слитый файл, и ни один файл шаблона не пишется сквозь неё.

`All.sln` меняется через `dotnet sln`, по проекту, и как текст не сливается: `dotnet sln add` каждый раз даёт
проекту новый GUID. Его проекты сливаются так же, как строки файла: проект, который шаблон добавил, входит в него,
проект, который шаблон убрал, уходит, если его не добавила команда, а проект, который убрала команда, не
возвращается.

### Слияние через git

В готовом решении в корне его git-репозитория `dotskit new` и `dotskit upgrade` сливают через git, тем же
трёхсторонним слиянием:

- ветка `dotskit/template` хранит то, что шаблон дал решению, по коммиту на версию. git знает базу, когда в
  последнем коммите ветки лежат файлы базы и этот коммит есть в истории рабочей ветки; иначе, как в первый раз
  или на другой ветке, база коммитится туда и принимается рабочей веткой так, как это сделал бы
  `git merge -s ours`: коммит слияния с деревом самой ветки и базой вторым родителем, сделанный через
  `git commit-tree` и `git update-ref`. Файлы решения не меняются, а git с этого момента знает базу. Хуки
  коммита команды за запуск не срабатывают (pre-commit, prepare-commit-msg, commit-msg, pre-merge-commit,
  post-merge); хуки ссылок и индекса, например reference-transaction, git запускает как обычно. Коммиты dotskit
  не подписываются. `git merge --abort` этот коммит не снимает, файлов он
  не меняет. Слияние не начинается поверх дерева, которое изменилось после старта команды, например файла,
  сохранённого, пока план ждал ответа. Если упал следующий шаг, команда выполняет `git reset --hard` к коммиту,
  с которого начала, и возвращает ветку на место: так снимаются слияние, этот коммит и все отслеживаемые файлы,
  которые изменил запуск, а файлы, которых git не отслеживает, остаются. Отслеживаемый файл, изменённый руками,
  пока идёт слияние, снимается вместе с ними. Если git отказывает, например из-за `index.lock` от остановленного
  git, ошибка называет команды, которые сделают это руками;
- команда коммитит туда новый вывод шаблона и выполняет `git merge --no-ff --no-commit dotskit/template`. git
  берёт правки шаблона и правки команды, следит за файлами, которые шаблон перенёс, и помечает строки, которые
  изменили обе стороны, для IDE или `git mergetool`: `<<<<<<< solution`, `=======`, `>>>>>>> template`. IDE
  читает базу из индекса и рисует свои панели. У файла, который добавили обе стороны, базы нет - версия шаблона,
  от которой обновляются, его не содержала, - а база обязана быть реальным состоянием файла: «взять базу» должно
  дать рабочий файл, поэтому это никогда не вычисленное пересечение двух сторон - такого файла не существовало, и
  для кода он был бы сломан. Индекс получает сторону решения как базу: результат начинается с версии решения
  (слева нет изменений), а сторона шаблона показывается как одно изменение, переписывающее файл (справа). Решение
  бинарно: принять предложение и взять сторону шаблона («принять обе» делает то же - берётся последняя версия)
  или оставить файл решения; обновление по выпуску за раз, `--to` через выпуск, который ввёл файл, даёт ему
  настоящую базу и такого конфликта не будет. Слияние остаётся незакоммиченным: его можно
  посмотреть, закоммитить или отменить через `git merge --abort`;
- `--conflict-style zdiff3` помечает каждый конфликт ещё и с его базой, как пишет zdiff3 (`||||||| base`): для IDE
  или читателя, которые берут базу из файла, а не из индекса. По умолчанию - plain;
- план показывает собственные изменения шаблона: какие файлы он добавляет, меняет или удаляет;
- то, что git решения игнорирует по любому из своих `.gitignore` (в том числе локальные секреты), и
  `All.sln` в ветку не попадают; манифест и `All.sln`, которые пишет команда, входят в слияние, поэтому
  `git merge --abort` возвращает и их;
- `--force` сливает с `-X theirs`: строка, которую изменили обе стороны, берётся из шаблона, и план называет каждый
  файл, где строки команды уступили; файл, который одна сторона удалила, а другая изменила, тоже идёт за шаблоном -
  удаляется там, где удалил шаблон, и берётся версия шаблона там, где удаляла команда, - и план называет его вместе
  с ними;
- файл, который изменили обе стороны, сливает драйвер слияния dotskit, заданный только этому слиянию: база, файл
  команды и файл шаблона сначала приводятся к стилю шаблона - без BOM, без пробелов в конце строк, с переводом
  строки в конце, - поэтому одна смена стиля не конфликтует ни с чем, что написала команда, а слитый файл
  получает стиль. Файл решения сохраняет BOM, а слитый файл - концы строк файла команды. Перенос строки двумя
  пробелами в конце строки Markdown в файле, который изменили обе стороны, теряется: пишите его обратной косой
  чертой. Файл со своим слиянием в `.gitattributes`, как у Git LFS, его сохраняет.

Что после этого показывает git: `git log dotskit/template` - что каждая версия шаблона дала решению;
`git diff dotskit/template HEAD` после коммита слияния - собственные правки команды поверх шаблона её версии,
и ничего больше.

`--allow-dirty` работает при незакоммиченных изменениях: они, вместе с неотслеживаемыми файлами, коммитятся
рядом с запуском через plumbing - без хуков, без переключения веток, - и участвуют в слиянии как любая
закоммиченная сторона: конфликт ваших правок с шаблоном помечается как любой другой, а у коммита слияния они
становятся родителем. Упавший до слияния запуск возвращает их незакоммиченными через `git reset --mixed`;
`--force` с флагом отказывает - ему нужны строки команды в коммите.

### Команды git, которые запускает dotskit

Каждая команда git, которую запускает инструмент, по тому, что она делает с репозиторием решения. Инструменту
нужен git 2.35 или новее: `--conflict-style zdiff3` использует zdiff3, который появился в 2.35. Список путей идёт в git
файлом (`--pathspec-from-file`), а не командной строкой, поэтому влезает решение любого размера.

| Что делает с репозиторием | Команда | Зачем |
|---|---|---|
| ничего, читает | `git status --porcelain` | чистое рабочее дерево перед записью |
| | `git rev-parse --show-prefix` | лежит ли решение в корне своего репозитория, для слияния через git |
| | `git ls-files -v` | файлы с пометкой `assume-unchanged` или `skip-worktree`: git прячет их локальные правки от `git status`, а откат их потерял бы, поэтому команда отказывает |
| | `git rev-parse` (`HEAD`, `--absolute-git-dir`, `MERGE_HEAD`, ветка, дерево коммита) | где стоят решение и ветка |
| | `git merge-base --is-ancestor` | есть ли в рабочей ветке последний коммит ветки |
| | `git config --path --get core.attributesFile` | глобальные атрибуты пользователя, они остаются под атрибутами драйвера |
| | `git ls-files --others --ignored --exclude-standard` | файлы, которые git решения игнорирует, - их не пишут |
| | `git diff --name-only --diff-filter=U` | файлы, оставшиеся в конфликте |
| | `git ls-files -u` | стороны каждого конфликта: конфликт без стороны решения, где шаблон сменил только стиль - концы строк, пробелы, BOM, - разрешается как удалление; конфликт без стороны шаблона при `--force` разрешается удаллением шаблона; конфликт без базы, добавленный обеими сторонами, - получает её из стороны решения |
| | `git update-index --index-info` | сторона решения как база файла, добавленного обеими сторонами: IDE открывает его со своим окном слияния |
| | `git diff --no-index -M` | файлы, которые шаблон перенёс, между двумя его выводами вне репозитория |
| | `git merge-file -p [--zdiff3]`, при `--force` ещё раз с `--theirs` | слияние файла собственным слиянием инструмента и драйвером, на копиях трёх сторон; `--zdiff3` - только с `--conflict-style zdiff3`; первый прогон считает конфликты, которые решает `--force` |
| | `git ls-remote --tags` | выпуски шаблона, для `init` на решении, которое не называет свою версию |
| пишет только объекты, через свой индекс | `git add -A`, `git rm --cached`, `git ls-files`, `git write-tree`, `git commit-tree` | коммит вывода шаблона; индекс и файлы решения не трогаются |
| двигает ветку `dotskit/template` | `git update-ref refs/heads/dotskit/template` | коммит нового вывода шаблона на ветке, только от вершины, прочитанной до того |
| коммитит в рабочую ветку, файлы не меняются | `git commit-tree -p HEAD -p <база>`, `git update-ref HEAD` | принятие базы - в первый раз или на другой ветке, без хуков коммита команды |
| коммитит в рабочую ветку, файлы не меняются | `git add -A`, `git write-tree`, `git commit-tree -p HEAD`, `git update-ref HEAD` | `--allow-dirty`: незакоммиченные изменения берутся в слияние, индекс становится их деревом |
| сливает в рабочее дерево без коммита | `git -c core.attributesFile=… -c merge.dotskit.driver=… [-c merge.conflictstyle=zdiff3] merge --no-ff --no-commit dotskit/template`, с `-X theirs` при `--force` | правки шаблона вместе с правками команды, драйвером `dotskit merge-driver`, заданным только этому слиянию; `merge.conflictstyle=zdiff3` - только с `--conflict-style zdiff3`; при `--force` драйвер называет через `DOTSKIT_TAKEN_REPORT` каждый файл, чей конфликт взял строки шаблона, и план их перечисляет |
| стейджит | `git add` | манифест, `All.sln` и файлы, исправленные починкой, входят в слияние; при `--force` вместе с `git checkout --theirs` разрешает файл, который удалила команда, а шаблон изменил, - версией шаблона |
| удаляет из дерева и индекса | `git rm -f` | файл, который команда удалила, а шаблон только переоформил - концы строк, пробелы, BOM, - остаётся удалённым, а не конфликтом; при `--force` файл, который команда изменила, а шаблон удалил, уходит за шаблоном |
| откатывает упавший запуск | `git reset --hard`, `git update-ref` (или `-d`); `git reset --mixed` после коммита `--allow-dirty`; `git rev-parse --git-path index.lock`, если git отказал | рабочая ветка, её отслеживаемые файлы и ветка `dotskit/template` - там, где были до запуска; незакоммиченные изменения - снова незакоммиченными |

Инструмент никогда не коммитит слияние, не пушит и не переключает ветки: слияние команда смотрит, коммитит или
отменяет сама.

## Манифест

`.dotskit/manifest.json` хранит, из чего сгенерировано решение: версию шаблона, аргументы решения и
аргументы каждого сервиса. Коммитьте его вместе с решением: каждая следующая команда восстанавливает по нему
базу.

Манифест хранит порт каждого сервиса: без `--HttpPort` порт берётся один раз и пишется в манифест, а сервис
сохраняет порт, когда следующая команда добавляет ему флаг. Инструмент называет первый порт от 5000, которого
нет у других сервисов решения; один `dotnet new` оставляет выбор шаблону.

Флаг с частью в `Common` или в корне, например `--Storage`, становится флагом решения, когда он есть хотя бы
у одного сервиса. Имена решения, `--Database`, `--Deploy`, `--TestFramework`, `--Agent` и `--GitHubCiCd`
задаёт первая команда. Следующие команды берут их из манифеста; команда с другим значением одного из них
отклоняется.

`Infisical` и `Vault` - инфраструктура всего решения: сервис, добавленный через `dotskit new`, получает
хранилище секретов решения, даже если команда не повторяет его флаг. Возможности одного сервиса, например
`Storage`, `ClickHouse` или `MongoDB`, не копируются из другого сервиса.

Шаблон пишет манифест сам, когда генерирует решение: с 2.9 решение, созданное одним `dotnet new`, несёт
`.dotskit/manifest.json` с момента генерации, и `dotskit new` с `dotskit upgrade` работают по нему без
`dotskit init`. Сервис, сгенерированный в решение позже, в него не входит - шаблон пишет манифест только с
`--Solution`; `dotskit init` принимает его в манифест, прочитав по файлам.

## Решение, созданное без dotskit

`dotskit new` работает по манифесту. Шаблон пишет его при генерации с 2.9; у решения более ранней версии
или собранного из файлов шаблона руками манифеста нет, и его пишет `dotskit init`: читает решение, проверяет
прочитанное и после «да» записывает `.dotskit/manifest.json`, больше ничего.

Что он читает:

- версию шаблона из `DotNetSolutionKitVersion` в `Directory.Build.props`, она там с 2.7.0;
- имена из `src/services/*.All.sln`; где точка может относиться к любому из имён (`Acme.Corp.Shop`), - из
  имён образов в `deploy/build-images.sh` или из `-N` и `-P`, переданных команде;
- базу, развёртывание, тестовый фреймворк и агента по файлам, которые даёт только один вариант;
- флаги `Common` и корня по файлам, которые добавляет каждый флаг;
- каждый сервис в `src/services` с собственным API-проектом: его флаги по разделам `appsettings.json` и
  строкам, которые пишет только флаг, его порт по `launchSettings.json`.

Проверка: `init` генерирует решение заново по прочитанному, той же версией шаблона, и сравнивает с папкой -
«412 of 420 files of the template reproduced; these differ: ...». Отличающийся файл - это правка команды или
ошибка чтения; отчёт перечисляет такие файлы, чтобы человек разобрался до того, как на манифест что-то
опирается. Файлы, добавленные командой, не считаются, `All.sln` сравнивается по проектам. Шаблон этой версии
проверка ставит с nuget.org.

| Папка | Что делает `init` |
|---|---|
| пустая | ничего не пишет и называет `dotskit new -N <Company> -P <Product> -S <Service>` |
| нет `src/services/*.All.sln` | ничего не пишет: это не решение DotNetSolutionKit |
| решение 2.7 или новее, без манифеста | читает, проверяет, показывает манифест и отчёт, пишет после «да» |
| решение до 2.7, начиная с 1.0.0, которое не называет свою версию | при наличии `Common` сверяет его параллельно с последним патчем каждого минора до 2.7 по тегам репозитория, показывает долю файлов шаблона, которую воспроизводит каждый, ничего не пишет и называет ближайший: `dotskit init --template-version <он>`, а если это 1.0.0 - `2.0.0`, к которому код сначала приводится руками ([обновление](upgrading.ru.md#решение-v1)); без `Common` просит версию; с указанной версией проверка показывает, насколько она воспроизводит решение, сгенерированное с nuget.org или, до 2.6.1, из её тега на GitHub |
| сгенерировано из исходников шаблона (версия `source`) | ничего не пишет и просит выпуск, из которого оно взято, через `--template-version` |
| новее инструмента | ничего не пишет и называет `dotnet tool update -g SawKing.DotsKit.Tool` |
| более ранней мажорной версии, чем инструмент, кроме последнего выпуска предыдущей | ничего не пишет и называет инструмент мажорной версии решения |
| сервис другой версии, чем решение | ничего не пишет, называет сервис и его версию и просит версию, которой описать решение, через `--template-version`; с ней проверка покажет, что отличается |
| с манифестом, в котором есть все сервисы | ничего не пишет: «the manifest is current: 2.8.0, services Orders, Billing» |
| с манифестом и сервисом в `src/services`, которого в нём нет | добавляет сервис, прочитанный по его файлам, после той же проверки - шаблон пишет манифест только с `--Solution`, поэтому сюда попадает сервис, сгенерированный в решение |
| сервисы есть, а `Common` нет | пишет манифест без проверки и сообщает об этом: база и флаги, которые читаются из `Common`, берутся по умолчанию шаблона; `dotskit new` считает `Common` удалённым командой и не возвращает его |
| незакоммиченные изменения в git | работает: пишет только `.dotskit/` |

## Опции

| Опция | Что делает |
|---|---|
| `--yes` | пишет без вопроса, для CI |
| `--force` | решает конфликт строками шаблона; строки команды остаются в истории git, поэтому нужно чистое дерево, и `--allow-dirty` вместе с ним отказывает |
| `--no-build` | не собирает решение после записи |
| `--allow-dirty` | `new` и `upgrade`: работает при незакоммиченных изменениях - они коммитятся рядом с запуском и берутся в слияние; упавший запуск возвращает их незакоммиченными |
| `--template-version 2.x.y` | `init`: версия, которой создано решение, если оно её не называет |
| `--to 2.x.y` | `upgrade`: выпуск, к которому привести решение, не новее инструмента |
| `--conflict-style zdiff3` | `new` и `upgrade`: конфликт помечается ещё и с его базой (`\|\|\|\|\|\|\| base`), как пишет zdiff3; по умолчанию - plain |
| `--all-at-once` | `upgrade`: все части одним слиянием, вместо общих файлов сначала и затем по папке сервиса |
| `--part <part>` | `upgrade`: часть, которую берёт запуск, `shared`, `common/<проект>`, `capabilities` или последнее имя папки сервиса |

`DOTSKIT_TRACE=1` печатает в stderr каждый вызов `dotnet` и `git` с его временем: на что уходит время у
медленной команды.

## Коды выхода

| Код | Значение |
|---|---|
| `0` | записано, решение собирается; с `--no-build` - записано |
| `1` | отказ или сбой, причина одной строкой; ничего не записано, потому что ответ не «да»; или записано, но сборка упала или отменена |
| `2` | записано с конфликтами: разрешите их и соберите |

## Ограничения этой версии

- `dotskit new` работает в решении с манифестом: созданном `dotskit` или описанном `dotskit init`.
- `dotskit new` нужен манифест версии инструмента: решение более ранней версии сначала приводит к ней
  `dotskit upgrade`.
- Слиянию нужно решение в корне его git-репозитория. Если решение лежит в папке большего
  репозитория, команда отказывает ещё до плана: перенесите решение в свой репозиторий. Чистоту рабочего дерева команда
  проверяет по всему репозиторию.
