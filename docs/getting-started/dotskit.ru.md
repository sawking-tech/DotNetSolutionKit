# dotskit

`dotskit` - инструмент командной строки DotNetSolutionKit. Он генерирует решение шаблоном, добавляет в него
сервисы, а сервисам - флаги, и сохраняет правки команды: если команда и шаблон изменили один файл, он
сливает изменения так же, как git сливает ветки.

Шаблон работает и без инструмента, см. [генерацию решения](generating-a-solution.ru.md). Инструмент делает
то, чего один запуск `dotnet new` не может: добавляет флаг сервису, папка которого уже есть, обновляет файл,
который команда изменила, и записывает в решение, из чего оно сгенерировано.

## Установка

```bash
dotnet tool install -g SawKing.DotsKit.Tool
```

Инструмент публикуется с версии 2.8. dotskit X.Y.Z генерирует шаблоном X.Y.Z: он ставит пакет
`SawKing.DotNetSolutionKit` своей версии в отдельное хранилище шаблонов и не трогает шаблон, установленный
через `dotnet new install`.

## Команды

```bash
# в пустой папке: решение с первым сервисом
dotskit new -N MyCompany -P MyProduct -S Orders

# в решении: ещё один сервис, с именами, базой и развёртыванием решения
dotskit new -S Billing --Storage true

# в решении: флаг для существующего сервиса
dotskit new -S Orders --MongoDB true

# в решении, созданном без dotskit: описать его в манифесте
dotskit init

# в решении: привести его к версии шаблона, которой соответствует инструмент
dotskit upgrade
```

`dotskit new` по папке решает, создать решение или добавить в него: ищет `src/services/*.All.sln` в папке
и выше. `--Solution` не нужен и ничего не меняет.

Параметры шаблона передаются как есть, в короткой или длинной форме, в любом регистре: `-S`, `--Storage`,
`--storage`, `--api-gateway`. См. [параметры](generating-a-solution.ru.md#параметры).

## Что делает команда

1. Проверяет папку. Новое решение создаётся в пустой папке или рядом с файлами в чистом рабочем дереве git.
   Для добавления в решение нужен `.dotskit/manifest.json` версии инструмента и чистое рабочее дерево. В решении
   работает одна команда за раз: вторая, запущенная, пока первая работает, говорит об этом и ничего не меняет;
   блокировка уходит вместе с процессом, который её держит, даже если его убили.
2. Генерирует во временной папке то, что шаблон даёт для решения до команды (базу) и после неё.
3. Пофайлово сравнивает базу, новый вывод шаблона и решение и показывает план: каждый файл с тем, что с ним
   будет и почему, и проекты, которые добавятся в `All.sln` или уйдут из него.
4. Спрашивает перед записью. `--yes` пишет без вопроса.
5. Пишет все файлы или ни одного: ошибка или Ctrl+C посередине возвращают все файлы как были. Если процесс
   убит во время записи, рядом с файлами решения остаются `*.dotskit-new` и `*.dotskit-old`; `git status` их
   показывает, и следующая команда откажется работать с нечистым деревом, пока их не уберут через git.
6. Собирает `All.sln`.

Что происходит с файлом:

| В плане | Когда | Что записывается |
|---|---|---|
| `Add` | шаблон добавляет файл, которого в решении нет | файл шаблона |
| `Update` | команда файл не меняла | новый файл шаблона с окончаниями строк файла решения |
| `Merge` | файл изменили обе стороны, в строках порознь | обе правки |
| `Delete` | шаблон удалил файл, который команда не меняла | файл удаляется |
| `Kept` | одна сторона удалила файл, а другая изменила, или обе изменили двоичный файл | ничего: файл решения остаётся |
| `Conflict` | обе стороны изменили одни и те же строки или соседние | файл с обеими версиями между `<<<<<<< solution` и `>>>>>>> template` |

Файл решения, который игнорирует его git, в том числе локальный `appsettings.Secrets.json`, не пишет ни одно из
слияний. Новый файл шаблона, который git решения игнорировал бы, как файл секретов нового сервиса, пишут оба:
слияние через git, которое не кладёт его в ветку, пишет его рядом со слиянием, а ручной `git merge --abort` его
оставляет: git о нём не знает.

`All.sln` меняется через `dotnet sln`, по проекту, и как текст не сливается: `dotnet sln add` каждый раз даёт
проекту новый GUID. Его проекты сливаются так же, как строки файла: проект, который шаблон добавил, входит в него,
проект, который шаблон убрал, уходит, если его не добавила команда, а проект, который убрала команда, не
возвращается.

### Слияние через git

В готовом решении в корне его git-репозитория `dotskit new` и `dotskit upgrade` сливают через git, тем же
трёхсторонним слиянием:

- ветка `dotskit/template` хранит то, что шаблон дал решению, по коммиту на версию. git знает базу, когда в
  последнем коммите ветки лежат файлы базы и этот коммит есть в истории рабочей ветки; иначе, как в первый раз
  или на другой ветке, база коммитится туда и вливается в рабочую ветку через `git merge -s ours`: файлы
  решения не меняются, а git с этого момента знает базу. `git merge --abort` этот коммит не снимает, файлов он
  не меняет. Если шаг команды упал, команда сама снимает слияние, этот коммит и сдвиг ветки: git остаётся таким,
  каким был до запуска;
- команда коммитит туда новый вывод шаблона и выполняет `git merge --no-ff --no-commit dotskit/template`. git
  берёт правки шаблона и правки команды, следит за файлами, которые шаблон перенёс, и помечает строки, которые
  изменили обе стороны, для IDE или `git mergetool`. Слияние остаётся незакоммиченным: его можно посмотреть,
  закоммитить или отменить через `git merge --abort`;
- план показывает собственные изменения шаблона: какие файлы он добавляет, меняет или удаляет;
- то, что git решения игнорирует по любому из своих `.gitignore` (в том числе локальные секреты), и
  `All.sln` в ветку не попадают; манифест и `All.sln`, которые пишет команда, входят в слияние, поэтому
  `git merge --abort` возвращает и их;
- `--force` сливает с `-X theirs`: строка, которую изменили обе стороны, берётся из шаблона; файл, который одна
  сторона удалила, а другая изменила, остаётся конфликтом;
- файл, который изменили обе стороны, сливает драйвер слияния dotskit, заданный только этому слиянию: база, файл
  команды и файл шаблона сначала приводятся к стилю шаблона - без BOM, без пробелов в конце строк, с переводом
  строки в конце, - поэтому одна смена стиля не конфликтует ни с чем, что написала команда, а слитый файл
  получает стиль. Файл решения сохраняет BOM, а слитый файл - концы строк файла команды. `--merge files`
  делает то же. Перенос строки двумя пробелами в конце строки Markdown в файле, который изменили обе стороны,
  теряется: пишите его обратной косой чертой. Файл со своим слиянием в `.gitattributes`, как у Git LFS, его
  сохраняет.

Что после этого показывает git: `git log dotskit/template` - что каждая версия шаблона дала решению;
`git diff dotskit/template HEAD` после коммита слияния - собственные правки команды поверх шаблона её версии,
и ничего больше.

`--merge files` сливает силами самого инструмента, как в таблице выше, и пишет файлы без ветки и без
merge-коммита. `--allow-dirty` требует `--merge files`: слиянию через git нужно чистое дерево.

### Что dotskit запускает в git

Каждая команда git, которую запускает инструмент, по тому, что она делает с репозиторием решения. Список путей
идёт в git файлом (`--pathspec-from-file`), а не командной строкой, поэтому влезает решение любого размера.

| Что делает с репозиторием | Команда | Зачем |
|---|---|---|
| ничего, читает | `git status --porcelain` | чистое рабочее дерево перед записью |
| | `git rev-parse --show-prefix` | лежит ли решение в корне своего репозитория, для слияния через git |
| | `git rev-parse` (`HEAD`, `--absolute-git-dir`, `MERGE_HEAD`, ветка, дерево коммита) | где стоят решение и ветка |
| | `git merge-base --is-ancestor` | есть ли в рабочей ветке последний коммит ветки |
| | `git config --path --get core.attributesFile` | глобальные атрибуты пользователя, они остаются под атрибутами драйвера |
| | `git ls-files --others --ignored --exclude-standard` | файлы, которые git решения игнорирует, - их не пишут |
| | `git diff --name-only --diff-filter=U` | файлы, оставшиеся в конфликте |
| | `git diff --no-index -M` | файлы, которые шаблон перенёс, между двумя его выводами вне репозитория |
| | `git merge-file -p` | слияние файла в `--merge files` и драйвером, на копиях трёх сторон |
| | `git ls-remote --tags` | выпуски шаблона, для `init` на решении, которое не называет свою версию |
| пишет только объекты, через свой индекс | `git add -A`, `git rm --cached`, `git ls-files`, `git write-tree`, `git commit-tree` | коммит вывода шаблона; индекс и файлы решения не трогаются |
| двигает ветку `dotskit/template` | `git update-ref refs/heads/dotskit/template` | коммит нового вывода шаблона на ветке, только от вершины, прочитанной до того |
| коммитит в рабочую ветку, файлы не меняются | `git merge -s ours --no-ff` | принятие базы - в первый раз или на другой ветке |
| сливает в рабочее дерево без коммита | `git -c core.attributesFile=… -c merge.dotskit.driver=… merge --no-ff --no-commit dotskit/template`, с `-X theirs` при `--force` | правки шаблона вместе с правками команды, драйвером `dotskit merge-driver`, заданным только этому слиянию |
| стейджит | `git add` | манифест, `All.sln` и файлы, исправленные починкой, входят в слияние |
| откатывает упавший запуск | `git restore --source=HEAD --staged --worktree`, `git merge --abort`, `git reset --soft`, `git update-ref` (или `-d`) | застейдженное, слияние, коммит принятия базы и ветка - как до запуска |

Инструмент никогда не коммитит слияние, не пушит и не переключает ветки: слияние команда смотрит, коммитит или
отменяет сама.

## Манифест

`.dotskit/manifest.json` хранит, из чего сгенерировано решение: версию шаблона, аргументы решения и
аргументы каждого сервиса. Коммитьте его вместе с решением: каждая следующая команда восстанавливает по нему
базу.

Манифест хранит порт каждого сервиса. Без `--HttpPort` шаблон берёт случайный свободный порт, поэтому
инструмент выбирает порт один раз, первый от 5000, которого нет у других сервисов решения, и сервис сохраняет
его, когда следующая команда добавляет ему флаг.

Флаг с частью в `Common` или в корне, например `--Storage`, становится флагом решения, когда он есть хотя бы
у одного сервиса. Имена решения, `--Database`, `--Deploy`, `--TestFramework`, `--Agent` и `--GitHubCiCd`
задаёт первая команда. Следующие команды берут их из манифеста; команда с другим значением одного из них
отклоняется.

## Решение, созданное без dotskit

`dotskit new` работает по манифесту. У решения, созданного одним шаблоном или до 2.8, манифеста нет, и его
пишет `dotskit init`: читает решение, проверяет прочитанное и после «да» записывает `.dotskit/manifest.json`,
больше ничего.

Что он читает:

- версию шаблона из `DotNetSolutionKitVersion` в `Directory.Build.props`, она там с 2.7.0;
- имена из `src/services/*.All.sln`; где точка может относиться к любому из имён (`Acme.Corp.Shop`), - из
  имён образов в `deploy/build-images.sh` или из `-N` и `-P`, переданных команде;
- базу, развёртывание, тестовый фреймворк и агента по файлам, которые даёт только один вариант;
- флаги `Common` и корня по файлам, которые добавляет каждый флаг;
- каждый сервис в `src/services` с собственным API-проектом: его флаги по разделам `appsettings.json` и
  строкам, которые пишет только флаг, его порт по `launchSettings.json`.

Проверка: `init` генерирует решение заново по прочитанному, той же версией шаблона, и сравнивает с папкой -
«412 of 420 files of the template reproduced; these differ: ...». Отличающийся файл - это правка команды или
ошибка чтения; отчёт перечисляет такие файлы, чтобы человек разобрался до того, как на манифест что-то
опирается. Файлы, добавленные командой, не считаются, `All.sln` сравнивается по проектам. Шаблон этой версии
проверка ставит с nuget.org.

| Папка | Что делает `init` |
|---|---|
| пустая | ничего не пишет и называет `dotskit new -N <Company> -P <Product> -S <Service>` |
| нет `src/services/*.All.sln` | ничего не пишет: это не решение DotNetSolutionKit |
| решение 2.7 или новее, без манифеста | читает, проверяет, показывает манифест и отчёт, пишет после «да» |
| решение до 2.7, начиная с 1.0.0, которое не называет свою версию | при наличии `Common` сверяет его параллельно с последним патчем каждого минора до 2.7 по тегам репозитория, показывает долю файлов шаблона, которую воспроизводит каждый, ничего не пишет и называет ближайший: `dotskit init --template-version <он>`; без `Common` просит версию; с указанной версией проверка показывает, насколько она воспроизводит решение, сгенерированное с nuget.org или, до 2.6.1, из её тега на GitHub |
| сгенерировано из исходников шаблона (версия `source`) | ничего не пишет и просит выпуск, из которого оно взято, через `--template-version` |
| новее инструмента | ничего не пишет и называет `dotnet tool update -g SawKing.DotsKit.Tool` |
| более ранней мажорной версии, чем инструмент, кроме последнего выпуска предыдущей | ничего не пишет и называет инструмент мажорной версии решения |
| сервис другой версии, чем решение | ничего не пишет, называет сервис и его версию и просит версию, которой описать решение, через `--template-version`; с ней проверка покажет, что отличается |
| с манифестом, в котором есть все сервисы | ничего не пишет: «the manifest is current: 2.8.0, services Orders, Billing» |
| с манифестом и сервисом в `src/services`, которого в нём нет | добавляет сервис, прочитанный по его файлам, после той же проверки |
| сервисы есть, а `Common` нет | пишет манифест без проверки и сообщает об этом: база и флаги, которые читаются из `Common`, берутся по умолчанию шаблона; `dotskit new` считает `Common` удалённым командой и не возвращает его |
| незакоммиченные изменения в git | работает: пишет только `.dotskit/` |

## Обновление решения

```bash
dotnet tool update -g SawKing.DotsKit.Tool
dotskit upgrade
```

`dotskit upgrade` приводит решение к версии шаблона, которой соответствует инструмент, и сохраняет правки
команды. Это слияние `dotskit new`: база - манифест решения, сгенерированный версией решения, цель - тот же
манифест, сгенерированный версией инструмента. Нужен манифест - решению, созданному без `dotskit`, его даст
`dotskit init`, - и чистое рабочее дерево. Первые строки команды называют минорные версии, через которые она
проходит, и ссылку на английский [upgrading.md](upgrading.md) на GitHub, из master для выпуска и из dev для
предрелиза: его разделы для этих версий говорят, что решению, возможно, придётся поменять руками.

Что слияние добавляет для обновления:

- файл, который шаблон перенёс (`git diff -M` между двумя выводами), переезжает на новый путь вместе с
  правками команды, старый путь удаляется;
- файл, который шаблон удалил, удаляется, если команда его не меняла, и остаётся с пометкой в отчёте, если
  меняла;
- версии пакетов следуют разделу `packages` манифеста, см. ниже;
- после записи решение собирается; ссылки и строки `using` типов, которые шаблон перенёс, чинятся (ниже),
  оставшиеся ошибки выводятся по проектам.

Тип, который шаблон переносит в другой проект или пространство имён (так 3.0 переносит типы `Common`), ломает
код команды, который им пользуется. Инструмент читает, где лежит каждый публичный тип - проект и пространство
имён, - из обоих выводов шаблона, которые он и так генерирует для слияния. Поэтому шаг работает для любой
версии и не требует списка, который ведут руками. Тип прослеживается в своей области: копия типа в сервисе
ведёт в тот же сервис, тип общего кода - в общий код, поэтому сервис никогда не получает `using` или ссылку на
другой сервис.

Сразу после записи слияния, до любой сборки и при конфликтах тоже, каждый `using` кода решения, который называет
пространство имён, которого в шаблоне больше нет, заменяется на пространства, куда ушли его типы, а проект
получает ссылки на их проекты. Файл в конфликте, файл проекта в конфликте и пространство имён, которое
по-прежнему объявляет код самого решения, остаются сборке после разрешения конфликтов. При слиянии через git
изменённые файлы входят в слияние. Сборке после этого остаётся меньше, часто ничего. После сборки с ошибками:

- `using` пространства имён, которого в шаблоне больше нет (`CS0234`), заменяется на `using` пространств, куда
  ушли его типы, а проект получает ссылки на их проекты;
- ненайденный тип (`CS0246`), который шаблон перенёс из пространства имён, используемого файлом, получает свой
  `using` и ссылку на проект; тип команды с именем типа шаблона, тип, который шаблон не переносил или перенёс в
  два места, остаётся как есть;
- решение собирается снова, пока каждый круг находит, что починить: когда проект собрался, свои ошибки
  показывают проекты, которые на него ссылаются.

Отчёт говорит, сколько ссылок и строк `using` изменено; `git diff` их показывает. Починка идёт после того,
как слияние записано: если её запись не удалась, починка останавливается, и отчёт говорит почему. С
`--no-build` нет ни сборки, ни починки.

Какие версии: по одной мажорной за раз. dotskit X.y обновляет решение любого минора X и последнего минора
X-1. Для более старой мажорной инструмент называет шаги: инструмент мажорной версии решения, `dotskit
upgrade`, затем следующей мажорной, и так далее. Решение новее инструмента отклоняется с командой, которая
обновляет инструмент. Инструменты 2.x принимают и 1.0.0, единственный выпуск 1.x. Инструмент генерирует
версию из её пакета на nuget.org, где шаблон есть с 2.6.1, а более ранний выпуск - из архива его тега на
GitHub, поэтому решение любого выпуска начиная с 1.0.0 обновляется одинаково.

`--to 2.x.y` приводит решение к этому выпуску вместо версии инструмента: выпуск новее решения и не новее
инструмента. Решение, которое сильно отстало, можно вести по выпуску за шаг, каждый шаг - отдельное слияние
со сборкой после него:

```bash
dotskit upgrade --to 2.0.0
dotskit upgrade --to 2.1.0
dotskit upgrade
```

Версии пакетов приходят с обновлением настолько, насколько позволяет манифест:

```json
"packages": {
  "updates": "minor",
  "pinned": { "Npgsql": "8.0.4" }
}
```

| `updates` | Что приносит обновление |
|---|---|
| `minor` (по умолчанию) | патчи и минорные версии |
| `patch` | только патчи |
| `none` | версии пакетов решения не меняются |

Пакет из `pinned` остаётся на этой версии. Мажорная версия пакета приходит только с мажорной версией
шаблона. Пакет, которого в решении не было, приходит в версии шаблона. До слияния удержанные версии
записываются в сторону шаблона, поэтому эти строки не конфликтуют - версия, которую команда подняла сама,
конфликтует, если её не закрепить в `pinned`; в плане есть строка на каждый пакет,
который меняется или удержан, - «Npgsql: pinned on 8.0.4, the template brings 8.0.11». Если новому коду
шаблона нужна версия новее закреплённой, сборка падает, и отчёт называет проект.

Обновление делает механическую часть: текст файлов, переносы и удаления, версии пакетов, сборку. Должен ли
собственный код команды меняться вслед за шаблоном - например, свой обработчик рядом с тем, который шаблон
изменил, - решает команда, а показывают её тесты.

## Опции

| Опция | Что делает |
|---|---|
| `--yes` | пишет без вопроса, для CI |
| `--force` | решает конфликт строками шаблона; строки команды остаются в истории git |
| `--no-build` | не собирает решение после записи |
| `--allow-dirty` | работает при незакоммиченных изменениях |
| `--template-version 2.x.y` | `init`: версия, которой создано решение, если оно её не называет |
| `--to 2.x.y` | `upgrade`: выпуск, к которому привести решение, не новее инструмента |
| `--merge files` | `new` и `upgrade`: слить силами инструмента и записать файлы вместо слияния `dotskit/template` через git |

`DOTSKIT_TRACE=1` печатает в stderr каждый вызов `dotnet` и `git` с его временем: на что уходит время у
медленной команды.

## Коды выхода

| Код | Значение |
|---|---|
| `0` | записано, решение собирается; с `--no-build` - записано |
| `1` | отказ или сбой, причина одной строкой; ничего не записано, потому что ответ не «да»; или записано, но сборка упала или отменена |
| `2` | записано с конфликтами: разрешите их и соберите |

## Ограничения этой версии

- `dotskit new` работает в решении с манифестом: созданном `dotskit` или описанном `dotskit init`.
- `dotskit new` нужен манифест версии инструмента: решение более ранней версии сначала приводит к ней
  `dotskit upgrade`.
- Слиянию через git нужно решение в корне его git-репозитория. Если решение лежит в папке большего
  репозитория, команда отказывает ещё до плана и советует `--merge files`. Чистоту рабочего дерева команда
  проверяет по всему репозиторию.
