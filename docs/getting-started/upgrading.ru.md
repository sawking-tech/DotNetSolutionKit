# Версии шаблона

Версии шаблона отмечаются git-тегами по семантическому версионированию.

| Тег | Что это |
|---|---|
| `v1.0.0` | Шаблон до несовместимых изменений 2026 года. |
| `v2.0.0-preview.1` | Несовместимые изменения в процессе. |
| `v2.0.0` | Несовместимые изменения завершены и проверены. |

С 2.9 `dotskit upgrade` приводит решение любого выпуска начиная с `v1.0.0` к текущему и сохраняет правки
команды: `dotskit init --template-version` с выпуском, которым создано решение (`dotskit init` без версии назовёт
ближайший), затем `dotskit upgrade` или по
выпуску за шаг через `--to` ([dotskit](dotskit.ru.md#обновление-решения)). Разделы ниже - те же изменения
руками.

Что приносит каждая версия начиная с `v2.1.0`, написано в [version.json](../../version.json) и на
[странице релизов](https://github.com/sawking-tech/DotNetSolutionKit/releases); в таблице только версии,
которых там не объясняют.

Начиная с `v2.0.0` изменение либо сохраняет работоспособность сгенерированных решений, либо приходит с
коротким способом их обновить. Изменение, которое не может ни того, ни другого, выходит новой мажорной
версией.

## Из какой версии решение

`Directory.Build.props` в корне решения называет версию шаблона, из которой оно сгенерировано:

```xml
<DotNetSolutionKitVersion>2.7.0</DotNetSolutionKitVersion>
```

Значение записывается при упаковке шаблона, поэтому решение из пакета на nuget.org или из `.nupkg` релиза
называет этот релиз, а решение из исходников шаблона - `source`. Файл приходит вместе с решением
(`--Solution`): сервис, добавленный позже более новым шаблоном, его не меняет. В решении, сгенерированном
до появления свойства, его нет; версию подскажут даты на странице релизов.

Проект API каждого сервиса тоже называет версию, из которой сгенерирован, - `DotNetSolutionKitServiceVersion`.
Сервис, чья мажорная версия отличается от версии решения, не собирается: его код ждёт `Common` своего мажора,
и ошибка называет, какие версии встретились. Сначала обновите решение, потом генерируйте сервис. Решение,
сгенерированное до того, как версия стала записываться, считается 2.x; `source` с любой стороны не
проверяется.

Чтобы обновиться, прочитайте заметки к выпускам после этой версии. Сравнение своего `src/common` с
исходниками шаблона на теге `v<version>` показывает, что изменила ваша команда; сравнение этого тега с
новым - что изменил шаблон.

Файлы, с которых начинаются собственные механизмы шаблона, его `README` и `Directory.Build.props` несут
строку с названием шаблона, его сайтом, лицензией MIT и автором. MIT требует сохранять уведомление об
авторских правах в копиях кода, эта строка и есть такое уведомление. Сгенерированным она файл не
называет: файл с пометкой `<auto-generated>` Roslyn считает сгенерированным кодом, большинство
анализаторов его пропускает, а предупреждения nullable в нём выключены.

## С v2.0 на v2.1

Сервис, сгенерированный из `v2.0.0`, без изменений собирается на `Common` из `v2.1.0`, и тесты `Common`
проходят: в `Common` только добавились типы и члены. Сервису, сгенерированному из `v2.1.0`, нужен этот
`Common`, поэтому сначала обновите `Common`:

1. Сгенерируйте решение из `v2.1.0` в пустую папку с `--Solution`, своими `-N` и `-P`, своими флагами и
   теми, что добавляете: `--Storage` и `--ClickHouse` добавляют файлы в `Common`.
2. Замените свои `src/common` и `src/Directory.Packages.props` сгенерированными. Если вы сами меняли
   `Common`, вместо замены сделайте слияние: diff двух папок покажет ваши изменения рядом с изменениями
   шаблона.
3. Возьмите из сгенерированного решения нужные вам новые файлы: `deploy/`, `.github/`, `tools/`. В ваших
   сервисах ничего менять не нужно.

Сервисы, которые генерируются после этого, получают те же флаги, без `--Solution`.

## С v2.5 на v2.6

Тестовая инфраструктура, на которой строятся тесты сервиса (контексты выполнения для тестов, тестовые
базы данных PostgreSQL, заглушки и проверки правил), переехала из `Common.Tests` в `Common.Testing` -
проект без тестового фреймворка. Пространства имён не изменились. После обновления `Common` тестовый
проект сервиса ссылается на `Common.Testing` вместо `Common.Tests`:

```xml
<ProjectReference Include="..\..\..\common\MyCompany.MyProduct.Common.Testing\MyCompany.MyProduct.Common.Testing.csproj" />
```

и в одном файле сообщает ему, как NUnit пропускает тест:

```csharp
internal static class TestSkipSetup
{
    [ModuleInitializer]
    internal static void UseNUnit() => TestSkip.Handler = Assert.Ignore;
}
```

## С v2.6 на v2.7

### Обработчики после коммита после сохранения без транзакции

До v2.6 фазы после коммита и отката запускались, только когда коммитилась или откатывалась
реляционная транзакция. EF Core отправляет одиночную команду без транзакции, поэтому `SaveChangesAsync` одного
изменения вне `BeginTransactionAsync` не запускал ни одного обработчика после коммита, а на in-memory
провайдере сервисных тестов они не запускались никогда. Теперь они запускаются, когда запись стала
окончательной. Обработчик, который молча не работал, начнёт работать: прочитайте обработчики после коммита
сервиса до переноса, а перенесите правку файлами `Persistence/EntityFramework/Events/DomainEventCompletion.cs`,
двумя интерсепторами и `DbContextBase.cs` из `Common.Infrastructure` этой версии.

### Слои сервиса видят то, что нужно их первому коду

В решении, сгенерированном до v2.7.0, слой приложения сервиса ссылается только на
`Common.Application` и домен, а инфраструктура и тесты не ссылаются на `Common.Contracts`. Все ссылки явные,
поэтому не собирается первый use case (он бросает `NotFoundException` из `Common` и отвечает типом из
`Common.Contracts`) и первый консьюмер сообщения шины. В каждом сервисе добавьте в
`<Service>.Application.csproj`:

```xml
<ProjectReference Include="..\..\..\common\MyCompany.MyProduct.Common\MyCompany.MyProduct.Common.csproj" />
<ProjectReference Include="..\..\..\common\MyCompany.MyProduct.Common.Contracts\MyCompany.MyProduct.Common.Contracts.csproj" />
```

а вторую строку - в `<Service>.Infrastructure.csproj` и `<Service>.Tests.csproj`.

### Одна in-memory база на тест

В решении, сгенерированном до v2.7.0, `InMemoryTestExecutionContext` берёт имя своей базы внутри колбэка `AddDbContext`, который
вызывается на каждый scope, поэтому `ArrangeAsync`, `ActAsync` и `AssertAsync` получают каждый свою пустую
базу: сервисный тест, который готовит данные или проверяет сохранённое, падает. В таком решении имя
берётся один раз, в конструкторе, в `Common.Testing/TestExecutionContext.cs`:

```csharp
public InMemoryTestExecutionContext()
{
    var database = $"TestDb_{Guid.NewGuid():N}";
    Services.AddDbContext<TDbContext>((sp, options) =>
    {
        options.UseInMemoryDatabase(database);
        // остальное как было
    });
}
```

### У фича-флагов нет эндпоинта записи

`PUT /api/v1/features/{key}` и `IFeatureStore` убраны: фича-флаг переключают правкой `features.json` на
диске или его значения в хранилище секретов, а сервисы её перечитывают. Эндпоинт писал в `features.json`, а он
лежит в образе: запись жила в одном контейнере до следующего деплоя, и значение из хранилища её перекрывало. В решении, где они есть, они остаются в его `src/common`; чтобы
убрать их, удалите действие из `FeaturesController`, `IFeatureStore.cs`, `FileFeatureStore.cs` и их
регистрацию в `AddPlatformFeatureManagement`.

### Без снимка хранилища секретов

`SnapshotPath` убран: секреты живут в своём источнике и в памяти работающего сервиса, копий нет. Сервис,
который стартует при упавшем хранилище, вне `Local` не стартует. Где был задан `Infisical__SnapshotPath` или
`Vault__SnapshotPath`, удалите ключ и файл снимка: в нём лежат секреты, а обновлять его больше некому.

## С v2.7 на v2.8

`dotskit upgrade` делает в решении v2.7 часть этих изменений, которая относится к файлам шаблона, и
сохраняет правки команды ([dotskit](dotskit.ru.md#обновление-решения)): `dotnet tool install -g
SawKing.DotsKit.Tool`, затем в решении `dotskit init` и `dotskit upgrade`. То, что касается собственного кода
команды, остаётся шагом вручную: атрибуты её собственных тестов и сервис, который она добавила в
`infrastructure.yml`, - он переезжает в `infra/`.

### Тесты сервиса носят один набор атрибутов

Тестовые проекты сервиса и шлюза получают `TestFramework.cs` - единственный файл, который знает тестовый
фреймворк, - вместо `GlobalUsings.cs` и `TestSkipSetup.cs`. Тесты носят его атрибуты - `[Test]`,
`[TestOf]`, `[Integration]`, `[RunsInParallel]`, `[RunsAlone]` - без `#if` по фреймворку, и скилл
`add-tests` пишет их так же. Перенос: взять `TestFramework.cs` из сервиса, сгенерированного v2.8 с тем же
`--TestFramework`, удалить два старых файла и заменить в тестах `[TestFixture]`,
`[Parallelizable(ParallelScope.All)]`, `[NonParallelizable]` и `[Category(TestCategories.Integration)]` на
ничего, `[RunsInParallel]`, `[RunsAlone]` и `[Integration]`; на xUnit - `[Fact]` и
`[Fact(DisplayName = ...)]` на `[Test]` и `[Test(Description = ...)]`, trait интеграционных тестов на
`[Integration]`, а `[Collection]`, чьё определение отключает параллельность, на `[RunsAlone]`. Под NUnit файл создаёт fixture на каждый тест:
fixture, которая держит состояние между тестами в полях или готовится в `[OneTimeSetUp]` на экземпляре,
должна сделать это состояние статическим или перенести его в каждый тест.

### База выбирается в одном месте

`DatabaseProvider` в `Common.Infrastructure` - единственное место, которое знает, на PostgreSQL решение
или на SQL Server, а настройка Hangfire сервиса переехала в `DependencyInjection.BackgroundJobs.cs`. Поведение сервиса не
меняется, поэтому существующее решение работает как есть; чтобы взять изменение, скопируйте
`Persistence/DatabaseProvider.cs` из решения, сгенерированного v2.8 с тем же `--Database`, и замените вызовы
провайдера в `DependencyInjection.cs` сервиса, его фабрике `DbContext` для времени разработки и
`HealthChecks.cs` на вызовы `DatabaseProvider`, как в сервисе, сгенерированном v2.8.

### Версии, которые приносит флаг, лежат в отдельном файле

Строки `PackageVersion` флага переехали из `src/Directory.Packages.props` в `src/package-versions/<флаг>.props`,
а общий файл подключает их по маске: флаг, добавленный позже, добавляет файл, а не правит общий. Готовое
решение работает как есть; чтобы взять изменение, скопируйте `src/package-versions/` из решения,
сгенерированного v2.8 с теми же флагами, уберите эти строки из своего `Directory.Packages.props`, добавьте
`<Import Project="package-versions/*.props" />` перед `</Project>`, а в `Dockerfile` - строку
`COPY src/package-versions/ src/package-versions/` после строки, которая копирует `Directory.Packages.props`.

### Каждая часть инфраструктуры - отдельный файл

`deploy/compose/infrastructure.yml` разделён на `deploy/compose/infra/<часть>.yml` - база данных, RabbitMQ и
то, что приносит флаг, - а `compose.sh` и `bluegreen.sh` берут все файлы этой папки; список инфраструктуры
`bluegreen.sh` теперь читает из них, а не перечисляет сам. Чтобы взять изменение, скопируйте
`deploy/compose/infra/`, `compose.sh` и `bluegreen.sh` из решения, сгенерированного v2.8 с теми же флагами,
перенесите в `infra/` сервисы, которые вы сами добавили в `infrastructure.yml`, и удалите этот файл.

### Тестовые серверы - скрипты, одинаковые в CI и на машине разработчика

`ci.yml` решения поднимал каждый тестовый сервер своим `docker run` и задавал переменные `TEST_*` в джобе;
теперь каждый сервер - скрипт в `tests/servers/` (`start`, `ready`, `logs`, `down`), а `tests/servers/up.sh`
поднимает их все, ждёт готовности и отдаёт переменные: в CI через `$GITHUB_ENV`, локально через
`eval "$(bash tests/servers/up.sh)"`. Порты ушли со стандартных (PostgreSQL 15433, SQL Server 11433, ClickHouse 18123,
MongoDB 17017, MailHog 11025 и 18025, S3 18333, Vault 18200), чтобы не встречаться с локальным стеком. Чтобы взять изменение,
скопируйте `tests/servers/` и шаги тестов `ci.yml` из решения, сгенерированного v2.8 с теми же флагами.

### Сервис сам добавляется в All.sln

Сервис, сгенерированный в решение, сам добавляет свои проекты в `All.sln`; `dotnet new` спрашивает, прежде
чем выполнить эту команду, а `--allow-scripts yes` выполняет её без вопроса, в скриптах и CI.
`src/services/manual-add-projects.sh` из шаблона убран; в готовом решении его можно удалить.

### Контейнеры сервиса работают с корневой файловой системой только для чтения

Контейнеры сервиса и шлюза работают с корневой файловой системой только для чтения и `/tmp` в памяти, в
docker compose и в Kubernetes. Сервис пишет лог в консоль: файловый лог `logs/app.log` переехал из
`appsettings.json` в `appsettings.Local.json`, для машины разработчика. Сервис команды, который пишет файлы
в своём контейнере, пишет их в `/tmp`, а если они должны пережить контейнер - в объектное хранилище. Чтобы
взять изменение, скопируйте из решения, сгенерированного v2.8, настройки каждого сервиса и шлюза в `deploy/compose.yml` или
`deploy/k8s.yaml` и раздел `Serilog` из `appsettings.json` и `appsettings.Local.json`.

### Решение генерируется с --Solution

Решение генерируется с `--Solution`, а каждый следующий сервис - без него. `-M false` прежних версий
по-прежнему означает то же и скрыт из `dotnet new --help`; он уйдёт в 3.0. В решении менять нечего; в своих
скриптах `-M false` можно заменить на `--Solution`.

## Решение v1

`dotskit upgrade` приводит его к `v2` и дальше, сохраняя правки команды. `dotnet new ... --force` поверх
него перезаписывает файлы, которые изменила `v2`, и оставляет остальные, а результат не собирается. Список
ниже - что изменилось, для правки руками.

## Что изменилось в v2

Сборка и проекты:

- Версии пакетов объявляются один раз, в `src/Directory.Packages.props`; `.csproj` ссылается на пакет
  только по имени.
- Проект видит только те проекты, на которые ссылается сам: транзитивные ссылки на проекты отключены.
  Проект API добирается до домена через проект приложения.
- `Common.Contracts` зависит от `Common`, а не наоборот; контекст пользователя и выполнения переехал в
  `Common` (`Domain/Context`).
- Версия задаётся вручную в `version.json` вместо Nerdbank.GitVersioning; см.
  [ADR-004](../adr/004-product-version-by-hand.md).
- Один `Dockerfile` в корне решения собирает все сервисы.

Хост сервиса:

- Веб-слой берётся из `Common.Web`: `AddPlatformLogging`, `AddPlatformWebApi` и `UsePlatformPipeline`
  заменяют собственные файлы `Setup` сервиса для логирования, JSON, CORS, Swagger, валидации и конвейера.
  См. [веб-слой](../architecture/web-layer.md).
- Приложение собирается в `SchemaHost.Build`, который вызывает `Program`.
- DI-контейнер проверяется при старте в каждом окружении.
- `DbContext` сервиса регистрируется через `AddDbContext`, без пула.

Контракт API:

- Ошибки - это problem details по RFC 9457; обёртки `ErrorResponse` больше нет. См.
  [ошибки](../architecture/errors.md).
- Перечисления пишутся именами вместо чисел, а значения `DateTimeOffset` - в UTC с `Z` вместо смещения
  сервера. См. [JSON](../architecture/web-layer.ru.md#json).
- Маршрут без сегмента `api/v{n}` попадает только в документ Swagger `all`; раньше он считался `v1`.
  См. [документы Swagger](../architecture/web-layer.ru.md#документы-swagger).
- Неудачная валидация отвечает 422, а не 400.
- Эндпоинты здоровья - `/health` и `/ready` вместо `/healthz` и `/readyz`.

Код:

- `TenantId` заменяет `PartnerId` в контексте пользователя.
- Доменные события обрабатывают каскад, поднятый обработчиками до сохранения, запускают обработчики после
  коммита и при откате в новом scope и доходят до задач Hangfire. См.
  [доменные события](../architecture/domain-events.md).
- Проверка прав и `IPermissionService` переехали в `Common`; по умолчанию права берутся из claims токена.
  См. [аутентификация и права](../architecture/authentication-and-permissions.md).
