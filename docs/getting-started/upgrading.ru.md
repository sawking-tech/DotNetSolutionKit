# Версии шаблона

Версии шаблона отмечаются git-тегами по семантическому версионированию.

| Тег | Что это |
|---|---|
| `v1.0.0` | Шаблон до несовместимых изменений 2026 года. |
| `v2.0.0-preview.1` | Несовместимые изменения в процессе. |
| `v2.0.0` | Несовместимые изменения завершены и проверены. |

С 2.9 `dotskit upgrade` приводит решение выпуска 2.x к текущему, и git сохраняет правки команды там, где они
сливаются с правками шаблона; остальное - конфликты, которые разрешает команда. Сначала `dotskit init
--template-version` с выпуском, которым создано решение (`dotskit init` без версии назовёт ближайший), затем
`dotskit upgrade`, по части за запуск. Внутри одной мажорной версии это работает от её первого выпуска до любого
следующего; `--to` останавливается на промежуточном выпуске - для команды, которая хочет сначала собрать и
проверить решение там ([выше](#ход-обновления)). Решение v1
сначала руками приводится к `v2.0.0`, [ниже](#решение-v1). Разделы ниже - те же изменения руками.

Что приносит каждая версия начиная с `v2.1.0`, написано в [version.json](../../version.json) и на
[странице релизов](https://github.com/sawking-tech/DotNetSolutionKit/releases); в таблице только версии,
которых там не объясняют.

Начиная с `v2.0.0` изменение либо сохраняет работоспособность сгенерированных решений, либо приходит с
коротким способом их обновить. Изменение, которое не может ни того, ни другого, выходит новой мажорной
версией.

## Ход обновления

```bash
dotnet tool update -g SawKing.DotsKit.Tool
dotskit upgrade
```

Что делает обновление, от простого к тому, что команде иначе пришлось бы делать руками:

| | Что делает обновление |
|---|---|
| Одна команда | `dotskit upgrade`, оттуда, где стоит решение, к версии шаблона, которой соответствует инструмент |
| По части за запуск | общие файлы, затем каждый проект `Common`, затем по сервису: конфликты одного слоя за раз, а не всего расстояния |
| Любое расстояние внутри мажора | от первого выпуска мажора до любого следующего; `--to 2.x.y` останавливается на промежуточном - для команды, которая хочет сначала собрать и проверить решение там |
| Обычное слияние git | вывод шаблона лежит веткой `dotskit/template`, а слияние - это `git merge`: IDE, `git mergetool` и `git merge --abort` работают как всегда, и коммитит слияние команда |
| Откат средствами git | упавший запуск снимается `git reset --hard` к коммиту, с которого начал, а ветка возвращается на место |
| **`using` и пространства имён перенесённых типов** | тип, который шаблон перенёс в другой проект или пространство имён, прослеживается в собственном коде команды: его `using` заменяется, полное имя получает новое пространство, а проект - ссылку; на одном реальном решении таких правок 419, и ни одной руками |
| **Ссылки и версии** | ссылки между проектами шаблона, версии пакетов центрального управления и состав `All.sln` приводятся к тому, что есть в новой версии |

Что проверено. Решение, которого никто не менял, - собственный вывод шаблона - проходит от любого выпуска
мажорной версии до любого следующего без конфликтов и ошибок: на чистом решении `2.0`, доведённом до текущей
версии, напрямую за 12 запусков и с остановкой на `2.7.0` за 23, каждая часть слилась чисто, решение собирается
и его тесты проходят. На решении, которое команда месяцами меняла, сторона шаблона сливается так же, а то, что
команда изменила в тех же строках, становится конфликтом для команды - здесь инструмент не угадывает.

Разделы ниже говорят, как каждое из этого работает, чего инструмент не делает и что решению, возможно,
придётся поменять руками.

`dotskit upgrade` приводит решение к версии шаблона, которой соответствует инструмент, и сохраняет правки
команды. Это слияние `dotskit new`: база - манифест решения, сгенерированный версией решения, цель - тот же
манифест, сгенерированный версией инструмента. Нужен манифест - решению, созданному без `dotskit`, его даст
`dotskit init`, - и чистое рабочее дерево. Первые строки команды называют минорные версии, через которые она
проходит, и ссылку на английский [upgrading.md](upgrading.md) на GitHub, из master для выпуска и из dev для
предрелиза: его разделы для этих версий говорят, что решению, возможно, придётся поменять руками.

Что слияние добавляет для обновления:

- файл, который шаблон перенёс (`git diff -M` между двумя выводами), переезжает на новый путь вместе с
  правками команды, старый путь удаляется;
- файл, который шаблон удалил, удаляется, если команда его не меняла, и остаётся с пометкой в отчёте, если
  меняла;
- версии пакетов следуют разделу `packages` манифеста, см. ниже;
- после записи решение собирается; ссылки и строки `using` типов, которые шаблон перенёс, чинятся (ниже),
  оставшиеся ошибки выводятся по проектам.

Тип, который шаблон переносит в другой проект или пространство имён (так 3.0 переносит типы `Common`), ломает
код команды, который им пользуется. Инструмент читает, где лежит каждый публичный тип - проект и пространство
имён, - из обоих выводов шаблона, которые он и так генерирует для слияния. Поэтому шаг работает для любой
версии и не требует списка, который ведут руками. Тип прослеживается в своей области: копия типа в сервисе
ведёт в тот же сервис, тип общего кода - в общий код, поэтому сервис никогда не получает `using` или ссылку на
другой сервис.

Сразу после записи слияния проект шаблона ссылается на те проекты шаблона, на которые ссылается его новая
версия, не больше и не меньше: ссылка, которую прежняя версия дала неверно, уходит, новая приходит, ссылка на
проект команды остаётся; при центральном управлении пакетами версия, которую ещё называет `PackageReference`,
уходит в `src/Directory.Packages.props` и уходит из проекта. Версия, уже объявленная там или в файле флага в
`src/package-versions`, второй раз не объявляется; своя версия проекта, если она другая, остаётся его
`VersionOverride`, так что ни один пакет не меняет версию. Папка, чей `Directory.Build.props` выключает
центральное управление, проект в конфликте и проект части, до которой ещё не дошли, остаются как есть. Пакет,
который шаблон убрал, сохраняет версию, пока на него ссылается проект команды. Затем, до любой сборки и при конфликтах тоже,
каждый `using` кода решения, который называет
пространство имён, которого в шаблоне больше нет, заменяется на пространства, куда ушли типы, названные в файле,
и только на их проекты файл получает ссылки - домен не ссылается на инфраструктуру из-за пространства, чьи типы
разошлись в обе. Файл, который не называет ни одного перенесённого типа, например только зовёт
extension-методы, получает все направления. Тип, который шаблон перенёс в другое пространство имён, а код называет полным
именем - как тип, в `new`, `typeof`, аргументе дженерика или перед статическим членом, с `global::` или без,
в алиасе или статическом `using` - получает новое пространство имён на месте, по синтаксису C#, а проект - ссылку;
`cref` XML-комментария и код под неактивным `#if` остаются сборке. Файл в конфликте, файл проекта в конфликте и пространство имён, которое
по-прежнему объявляет код самого решения, остаются сборке после разрешения конфликтов. При слиянии через git
изменённые файлы входят в слияние. Сборке после этого остаётся меньше, часто ничего. После сборки с ошибками:

- `using` пространства имён, которого в шаблоне больше нет (`CS0234`), заменяется на `using` пространств, куда
  ушли его типы, а проект получает ссылки на их проекты;
- ненайденный тип (`CS0246`), который шаблон перенёс из пространства имён, используемого файлом, получает свой
  `using` и ссылку на проект; тип команды с именем типа шаблона, тип, который шаблон не переносил или перенёс в
  два места, остаётся как есть;
- решение собирается снова, пока каждый круг находит, что починить: когда проект собрался, свои ошибки
  показывают проекты, которые на него ссылаются.

Отчёт перечисляет по проектам изменённые строки `using` и полные имена и добавленные ссылки; `git diff` их показывает. Починка идёт после того,
как слияние записано. Починка до сборки - шаг записи: в слиянии через git сбой или Ctrl+C на ней откатывают
запуск; в слиянии файлами файлы остаются записанными, и ошибка говорит об этом. Если не удалась запись
починки после упавшей сборки, починка останавливается, и отчёт говорит почему. С
`--no-build` нет ни сборки, ни починки.

### Какие версии закрывает обновление

Поддержанные переходы:

| Откуда | Куда | Поддержано |
|---|---|---|
| любой выпуск мажорной версии | любой следующий выпуск той же мажорной | да, одним `dotskit upgrade` |
| последний выпуск мажорной версии | первый выпуск следующей мажорной | да: 2.9 на 3.0, 3.x на 4.0 |
| выпуск в середине мажорной версии | следующая мажорная | через последний выпуск своей мажорной: 2.3 на 2.9, затем на 3.0 |
| мажорная версия | та, что через одну | нет: с 2.9 можно на 3.x, не на 4.x - идти по мажорной за раз |

dotskit X.y обновляет решение любого минора X и последнего минора X-1. Для более старой мажорной инструмент называет шаги: инструмент
мажорной версии решения, `dotskit upgrade`, затем следующей мажорной, и так далее. Решение новее инструмента
отклоняется с командой, которая обновляет инструмент. Откуда берётся версия, на всё это не влияет: инструмент
достаёт её из пакета на nuget.org, где шаблон лежит с 2.6.1, а всё более раннее - из архива тега на GitHub,
поэтому решение любого выпуска 2.x обновляется одинаково. Инструменты 2.x принимают и 1.0.0, единственный
выпуск 1.x, который отличается от 2.0.0 в большинстве файлов ([решение v1](#решение-v1)).

Внутри одной мажорной версии шаблон доводит решение её первого выпуска до любого следующего, поэтому обычный
путь - один `dotskit upgrade` оттуда, где стоит решение. `--to 2.x.y` вместо этого останавливается на
промежуточном выпуске, новее решения и не новее инструмента: более консервативный путь для команды, которая
хочет собрать решение и прогнать его тесты на этом выпуске, прежде чем идти дальше. Обновление в любом случае
идёт по частям, и шаг - это часть, а не всё расстояние.

```bash
dotskit upgrade --to 2.7.0   # по части 2.7.0 за запуск, пока манифест не скажет 2.7.0; там собрать и проверить
dotskit upgrade              # затем части версии инструмента, по запуску на каждую
```

Обновление идёт по одной части за запуск, чтобы команда разрешала конфликты одной части до следующей: сначала
общие части - корень с `deploy` и скриптами, затем файлы `src/common` и каждый его проект, проект раньше тех, что
на него ссылаются, затем `src/capabilities`, - потом по папке сервиса за шаг, по порядку. Проект, который шаблон
добавляет в `src/common`, - отдельная часть после тех, на кого он ссылается; части берёт первый запуск, и манифест
их помнит. Пакет, который шаблон убрал, сохраняет версию, пока на него ссылается проект оставшихся частей или
проект команды. Своя
папка команды - тоже часть, которой нечего сливать. Каждый запуск - то же слияние: новые файлы шаблона для уже слитых частей и
этой поверх его файлов для частей до неё. После слияния запуск чинит `using` и ссылки на проекты для типов,
которые шаблон перенёс между уже слитыми частями, во всех проектах решения и перечисляет их по проектам; тип,
который уходит в ещё не слитую часть, ждёт её, и `using` его namespace остаются. Затем решение собирается, и по
его ошибкам чинятся файлы команды, а файлы шаблона ещё не слитой части ждут её;
сервис, чьи файлы шаблона ждут своей части, до неё может не собираться, и сборка его называет. Манифест помнит
выпуск и слитые части, и следующий `dotskit upgrade` берёт следующую часть; `--part Orders` называет её сам, после
общих. Часть коммитится до следующей; последняя переводит манифест на выпуск, и `dotskit new` до тех пор ждёт.
Если последняя часть оставила конфликты, обновление остаётся открытым: после их разрешения и коммита
`dotskit upgrade` не меняет файлов шаблона, чинит `using` всего обновления, собирает решение и переводит манифест.
`--all-at-once` сливает все части за один запуск. Вывод шаблона для версии генерируется один раз и два дня
лежит в папке инструмента в локальных данных пользователя (`dotskit/outputs`), поэтому часть после первой обходится без генерации.

### Скорость работы

Обновление решения с семью сервисами - это десятки слияний, и каждое могло бы стоить полной генерации, полной
сборки и компиляции кода решения. Ни одно не стоит:

| | Как |
|---|---|
| Вывод шаблона | генерируется один раз на версию и хранится, ключ - сборка инструмента и манифест; каждая следующая часть копирует его, а не запускает `dotnet new` снова |
| Перенесённые шаблоном типы | читаются из двух сгенерированных выводов индексом «имя - проект и пространство имён», поэтому, чтобы знать, куда ушёл тип, ничего компилировать не нужно, и список руками не ведётся |
| Код команды | читается по синтаксису C# (Roslyn), а не компиляцией: полное имя находится и переписывается там, где написано, а строка или комментарий, где то же имя просто упомянуто, остаётся как есть |
| Коммит вывода шаблона | пишется через собственный индекс инструмента (`GIT_INDEX_FILE`), поэтому индекс и файлы решения он не трогает |
| Пути, которые идут в git | передаются файлом (`--pathspec-from-file`), поэтому решение любого размера влезает в одну команду |
| Сборка | идёт один раз на часть, а починка по её ошибкам - пока круг находит что-то новое |

На двух промышленных решениях выше часть занимала 30-37 секунд, всё расстояние - 20-23 минуты машинного
времени, а генерация запустилась дважды вместо десятков раз.

```bash
dotskit upgrade --to 2.7.0               # общая часть; разрешить, закоммитить
dotskit upgrade                          # следующая часть; разрешить, закоммитить
dotskit upgrade --part Billing           # названный сервис
dotskit upgrade --to 2.7.0 --all-at-once # или все части одним слиянием
```

Версии пакетов приходят с обновлением настолько, насколько позволяет манифест:

```json
"packages": {
  "updates": "minor",
  "pinned": { "Npgsql": "8.0.4" }
}
```

| `updates` | Что приносит обновление |
|---|---|
| `minor` (по умолчанию) | патчи и минорные версии |
| `patch` | только патчи |
| `none` | версии пакетов решения не меняются |

Пакет из `pinned` остаётся на этой версии. Мажорная версия пакета приходит только с мажорной версией
шаблона. Пакет, которого в решении не было, приходит в версии шаблона. До слияния удержанные версии
записываются в сторону шаблона, поэтому эти строки не конфликтуют - версия, которую команда подняла сама,
конфликтует, если её не закрепить в `pinned`; в плане есть строка на каждый пакет,
который меняется или удержан, - «Npgsql: pinned on 8.0.4, the template brings 8.0.11». Если новому коду
шаблона нужна версия новее закреплённой, сборка падает, и отчёт называет проект.

Обновление делает механическую часть: текст файлов, переносы и удаления, версии пакетов, сборку. Должен ли
собственный код команды меняться вслед за шаблоном - например, свой обработчик рядом с тем, который шаблон
изменил, - решает команда, а показывают её тесты.

## Версия, из которой решение

`Directory.Build.props` в корне решения называет версию шаблона, из которой оно сгенерировано:

```xml
<DotNetSolutionKitVersion>2.7.0</DotNetSolutionKitVersion>
```

Значение записывается при упаковке шаблона, поэтому решение из пакета на nuget.org или из `.nupkg` релиза
называет этот релиз, а решение из исходников шаблона - `source`. Файл приходит вместе с решением
(`--Solution`): сервис, добавленный позже более новым шаблоном, его не меняет. В решении, сгенерированном
до появления свойства, его нет; версию подскажут даты на странице релизов.

Проект API каждого сервиса тоже называет версию, из которой сгенерирован, - `DotNetSolutionKitServiceVersion`.
Сервис, чья мажорная версия отличается от версии решения, не собирается: его код ждёт `Common` своего мажора,
и ошибка называет, какие версии встретились. Сначала обновите решение, потом генерируйте сервис. Решение,
сгенерированное до того, как версия стала записываться, считается 2.x; `source` с любой стороны не
проверяется.

Чтобы обновиться, прочитайте заметки к выпускам после этой версии. Сравнение своего `src/common` с
исходниками шаблона на теге `v<version>` показывает, что изменила ваша команда; сравнение этого тега с
новым - что изменил шаблон.

Файлы, с которых начинаются собственные механизмы шаблона, его `README` и `Directory.Build.props` несут
строку с названием шаблона, его сайтом, лицензией MIT и автором. MIT требует сохранять уведомление об
авторских правах в копиях кода, эта строка и есть такое уведомление. Сгенерированным она файл не
называет: файл с пометкой `<auto-generated>` Roslyn считает сгенерированным кодом, большинство
анализаторов его пропускает, а предупреждения nullable в нём выключены.

## С любого выпуска 2.x

```bash
dotskit upgrade
```

Каждый файл шаблона - `Common`, capabilities, корень, `deploy`, скрипты,
workflow, тестовые серверы, версии пакетов - сливает инструмент, из какого бы выпуска решение ни шло.
Промежуточные выпуски ничего не просят у команды, которая пользуется шаблоном как есть.

Что остаётся команде - её собственный код и её решение:

| С выпуска | Что делает команда |
|---|---|
| `v2.7.0` | Post-commit обработчики доменных событий теперь срабатывают и после сохранения без транзакции. Обработчик команды, который молча не работал, начинает работать: перед обновлением прочитать post-commit обработчики каждого сервиса. |
| `v2.8.0` | Тесты сервиса носят атрибуты из `TestFramework.cs` (`[Test]`, `[Integration]`, `[RunsInParallel]`, `[RunsAlone]`). Тесты команды остаются на своих атрибутах, пока она их не заменит; под NUnit фикстуре, которая держит состояние между своими тестами в полях, нужно сделать это состояние статическим или перенести в каждый тест. |
| `v2.8.0` | Свой сервис команды, добавленный в `deploy/compose/infrastructure.yml`, переезжает в `deploy/compose/infra/`, по файлу на часть. |
| `v2.8.0` | `Infisical__SnapshotPath` и `Vault__SnapshotPath` убраны: удалить ключ там, где он задан, и удалить файл снимка - в нём лежат секреты, которые больше ничем не обновляются. |
| `v2.8.0` | Свой сервис команды, который пишет файлы в своём контейнере, пишет их в `/tmp` или в объектное хранилище, если они должны пережить контейнер: корневая файловая система только для чтения. |

Всё остальное, что изменили эти выпуски - где лежит файл, какой проект на какой ссылается, как разбита
инфраструктура, как стартуют тестовые серверы, - обновление приносит само.

## Решение v1

`v1.0.0` и `v2.0.0` различаются в большинстве файлов, и их слияние оставляет большую часть в конфликте: на
одном настоящем решении v1 - 96 файлов. Поэтому код приводится к `v2.0.0` по списку ниже, решение описывается
как `2.0.0` через `dotskit init --template-version 2.0.0`, а дальше его ведёт `dotskit upgrade`. `dotskit init`
называет этот путь, когда ближайший выпуск - `1.0.0`. `dotnet new ... --force` поверх решения v1 перезаписывает
файлы, которые изменила `v2`, и оставляет остальные, а результат не собирается.

Что даёт этот путь, по замеру на двух SaaS-платформах телекома, построенных на этом шаблоне и работающих в
проде месяцами; обе сгенерированы `v1`. Каждую описали как `1.0.0` и довели до текущей версии: одну напрямую
через `2.0.0`, другую с остановкой на `2.7.0`. Всё расстояние прошло, код команды доехал, тесты сервисов в
конце зелёные - на одной из них 2376 тестов. На прямом пути инструмент сам сделал 419 правок `using`,
пространств имён и ссылок, которых никому не пришлось делать руками. Чего он не сделал: архитектуру, которую
изменила `v2`, меняет команда. На одном решении код `Common` пользовался `Common.Contracts`, а `v2` развернула
эту зависимость - 42 ошибки компилятора остались человеку: ссылка обратно дала бы цикл, поэтому инструмент
отказывается её добавлять и говорит об этом.

## Изменения v2

Сборка и проекты:

- Версии пакетов объявляются один раз, в `src/Directory.Packages.props`; `.csproj` ссылается на пакет
  только по имени.
- Проект видит только те проекты, на которые ссылается сам: транзитивные ссылки на проекты отключены.
  Проект API добирается до домена через проект приложения.
- `Common.Contracts` зависит от `Common`, а не наоборот; контекст пользователя и выполнения переехал в
  `Common` (`Domain/Context`).
- Версия задаётся вручную в `version.json` вместо Nerdbank.GitVersioning; см.
  [ADR-004](../adr/004-product-version-by-hand.md).
- Один `Dockerfile` в корне решения собирает все сервисы.

Хост сервиса:

- Веб-слой берётся из `Common.Web`: `AddPlatformLogging`, `AddPlatformWebApi` и `UsePlatformPipeline`
  заменяют собственные файлы `Setup` сервиса для логирования, JSON, CORS, Swagger, валидации и конвейера.
  См. [веб-слой](../architecture/web-layer.md).
- Приложение собирается в `SchemaHost.Build`, который вызывает `Program`.
- DI-контейнер проверяется при старте в каждом окружении.
- `DbContext` сервиса регистрируется через `AddDbContext`, без пула.

Контракт API:

- Ошибки - это problem details по RFC 9457; обёртки `ErrorResponse` больше нет. См.
  [ошибки](../architecture/errors.md).
- Перечисления пишутся именами вместо чисел, а значения `DateTimeOffset` - в UTC с `Z` вместо смещения
  сервера. См. [JSON](../architecture/web-layer.ru.md#json).
- Маршрут без сегмента `api/v{n}` попадает только в документ Swagger `all`; раньше он считался `v1`.
  См. [документы Swagger](../architecture/web-layer.ru.md#документы-swagger).
- Неудачная валидация отвечает 422, а не 400.
- Эндпоинты здоровья - `/health` и `/ready` вместо `/healthz` и `/readyz`.

Код:

- `TenantId` заменяет `PartnerId` в контексте пользователя.
- Доменные события обрабатывают каскад, поднятый обработчиками до сохранения, запускают обработчики после
  коммита и при откате в новом scope и доходят до задач Hangfire. См.
  [доменные события](../architecture/domain-events.md).
- Проверка прав и `IPermissionService` переехали в `Common`; по умолчанию права берутся из claims токена.
  См. [аутентификация и права](../architecture/authentication-and-permissions.md).
