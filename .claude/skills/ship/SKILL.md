# Код попадает в `dev`

Мерж кнопкой в GitHub - единственный способ потерять подписи и проверки. Rebase-мерж пересоздаёт каждый
коммит: коммиттером становится `web-flow`, подпись слетает, а проверки остаются на прежнем SHA, которого в
истории уже нет. Поэтому `dev` принимает код только fast-forward.

## Шаги

1. **Ветка от `dev`.** `git checkout dev && git pull --ff-only && git checkout -b <тип>/<тема>`.
2. **Коммиты подписаны.** Проверка на каждом: `git log --format='%G?' -1` даёт `G`. Настройки - `user.signingkey`,
   `gpg.format=ssh`, `commit.gpgsign=true`. Если `N` - коммит не подписан, разбираться до пуша.
3. **Держать ветку на верхушке `dev`.** Локальный `git rebase dev` пересоздаёт коммиты **своим ключом**, подписи
   остаются. `git merge dev` не использовать: merge-коммит нарушит `required_linear_history` на `dev`.
4. **Пуш и PR.** PR нужен ради CI, а не ради кнопки: `on: pull_request` в `template.yml` запускает 20 джобов.
5. **Дождаться зелёного.** `gh pr checks <N> --watch`, или `bash scripts/wait-for-checks.sh <repo> <sha>` - скрипт
   падает на красной проверке, на коммите без проверок и на не успевшей за 40 минут.
6. **Fast-forward через воркфлоу:**
   `gh workflow run promote.yml -f source=<ветка> -f target=dev`, затем дождаться успеха прогона.
   `promote.yml` берёт `source`/`target` из входов без ограничений, поэтому годится любая ветка, не только `dev`/`master`.
7. **Проверить результат на `dev` по факту.** Две проверки, обе обязательные:
   - `git log -1 --format='%G?' origin/dev` даёт `G` - коммит приехал не пересозданным;
   - `git log --oneline dev..<ветка>` пуст - всё из ветки в `dev` доехало.

   Если `N` - сработал не тот путь. Если в `dev..<ветка>` что-то осталось - ff донёс не всё, и ветку удалять нельзя.
8. **Убрать за собой.** Ветку на remote - сразу: `gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<ветка>`,
   затем `git remote prune origin`, иначе удалённые ветки остаются remote-tracking refs и GitHub отдаёт по ним 404.
   Локальную - только после шага 7 и только когда работа прожила и вопросов не осталось: до этого она единственная
   копия коммитов на случай, если в `dev` окажется не то. Удалённая на remote и локальная ветка, которая на деле не
   доехала, - это потерянная работа.

## Почему не `gh pr merge`

У GitHub три стратегии мержа: merge, squash, rebase. Fast-forward среди них нет. На `dev` включён
`required_linear_history`, поэтому merge-коммит запрещён, squash ты не используешь (теряется атомарная история),
остаётся rebase - и он пересоздаёт коммиты.

Отключить rebase в настройках нельзя: GitHub требует хотя бы одну из двух линейных стратегий, и ответ на попытку -
422 `you need to allow either squash or rebase merge strategies`. Значит кнопка остаётся, а путь - через git.

## Барьер, на который опирается ff

Push с `GITHUB_TOKEN` не проходит через защиту ветки: required checks к ботам не применяются. Поэтому `promote.yml`
сам проверяет head до перемещения - `scripts/wait-for-checks.sh`. Все проверки, какие падали на коммите, должны быть
зелёными; `skipped` и `neutral` считаются проходом.

Ответственность за то, что все обязательные проверки запустились, - на мейнтейнере: он настраивает защиту. Скрипт
смотрит факт - что запустилось, то и зелёное.

## PR после ff

PR, чьи коммиты приехали в базу через ff, GitHub закрывает сам и помечает merged. Кнопку жать не нужно, ветку
на remote удалять всё равно нужно.

## Всё ли ветки едет в `dev`

ff переносит ветку целиком: другого способа у него нет - ветка должна быть продолжением `dev`, и приезжают все её
коммиты как есть. Склейки на входе не будет, поэтому коммиты в локальной ветке делаются атомарными и осмысленными
сразу (`git-style`).
