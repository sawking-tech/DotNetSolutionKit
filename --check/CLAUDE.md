# DotNetSolutionKit

Rules for an AI agent working in this repository. The product is a solution generated from the template: a
change is judged by what it does in a generated solution, not only by how the template's sources look.

## Layout

```
template/                  # the dotnet new template, packed as SawKing.DotNetSolutionKit
├── .template.config/      # template.json (parameters, conditions), dotnetcli.host.json (short names)
├── src/common/            # Common, what the services of a solution share
├── src/capabilities/      # a project per flag, Capabilities.<Name> (#101)
├── src/services/          # the service a generation names with -S
├── gateway/               # the API gateway of --ApiGateway
├── deploy/, tests/servers/, .github/   # what a generated solution ships beside its code
└── .claude/, CLAUDE.md    # the rules and skills a generated solution's agent gets - part of the product
docs/                      # the documentation, each page with a Russian twin <name>.ru.md
site/, index.html, ...     # the site
scripts/                   # the repository's own checks and the site's build
.github/workflows/         # template.yml checks every pull request; promote, release and site publish
```

## Code

The standards hold for every line of code in the repository - the template and `scripts/`.
They are proven here first: a rule that holds up may later go into the rules a generated solution's agent
gets; nothing comes the other way.

- Code, comments, XML docs and commit messages are in English.
- Clean architecture, modularity and SOLID wherever they fit: dependencies point inward, a module stands on
  its own and depends only on what it needs, and the layer that decides does not know the layer that stores
  or shows.
- Composition over inheritance: behaviour behind an interface, passed in through the constructor
  and put together in one place (the composition root), not overridden through `virtual`.
- A method does one thing. Long work is an orchestrator that names its steps and calls small methods or
  classes, not one long body.
- No magic values inline: a number, a path, a pattern or a name that means something is a named constant in
  the one place that owns it.
- Logic that decides is kept apart from what touches the outside (files, processes, the console), so it is
  tested without them.
- A change in behaviour comes with its test in the same commit; `git checkout <sha>` builds and passes.
- A failure tells the reader what is wrong and what to do, in one line: an exception or an exit code with a
  message, never a stack trace for an expected case.
- Before writing a file of a kind the repository already has (a template parameter and its conditions, a
  doc page, a workflow step), open two or three neighbours of that kind and follow
  them.
- A JSON file the template generates or `dotskit` writes explains its fields by metadata keys, `_comment_<Key>`
  after the field ([ADR-006](docs/adr/006-json-metadata-key-convention.md)); a field left empty on purpose always has one, and
  `template.yml` checks it.
- A file of the template that is XML (.csproj, .props) never has two hyphens inside a comment: MSBuild skips
  an invalid file it imports by mask without an error.
- The language of a script follows its work: shell for a script that mostly runs commands (dotnet, git),
  Python with nothing but its standard library for one that reads text (Markdown, a workflow's expressions,
  the site's HTML), C# for the product. The Python scripts move to C# files run by `dotnet run` in
  4.0, on .NET 10; on .NET 8 each would need a project of its own.

## Working on the template

- The template's sources are not the product; a generated solution is. A change is checked by generating
  with the flags it touches on and off, building with `-warnaserror` and running the tests.
- A flag is whole: its files are left out by `template.json` when it is off, its blocks in shared files sit
  under one condition, `template.yml` generates a combination with it, and it has a doc page in English and
  Russian. A flag that is given but does nothing says so at generation (a post-action), never silently.
- A conditional block is written in the comment syntax of its file: `//#if` in C# and JSON, `<!--#if -->` in
  XML, `#if` on a line of its own in YAML, `.env.example` and `.sln` (template.json runs the conditional
  operation on the last two).
- Compatibility: a solution generated by an earlier version keeps working. A change a user must act on is a
  section of `docs/getting-started/upgrading.md`; a breaking change waits for the next major version, even
  when nobody uses the template yet.
- New functionality of a flag lives in a project of its own, `Capabilities.<Name>` under `src/capabilities`,
  referenced by the services that use it, so a service carries only the packages of its flags; how shared
  code is laid out by kind is #101.
- What the template generates for a sample is in `DotNetSolutionKit.Samples`: a flag of the next release is
  an entry of `.samples/variants.json` since that version.

## Commands

```bash
# A generated solution from the template's sources, in a hive of its own
dotnet new install ./template --debug:custom-hive /tmp/hive --force
dotnet new DotNetSolutionKit -N Acme -P Shop -S Orders --Solution -o /tmp/acme --debug:custom-hive /tmp/hive
dotnet build /tmp/acme/src/services/Acme.Shop.All.sln -warnaserror

# The test servers of a generated solution, and its integration tests
eval "$(bash tests/servers/up.sh)" && dotnet test src/services/*.All.sln --filter "TestCategory=Integration"
```

A change to the template is checked on a generated solution: it builds with `-warnaserror`, its tests pass,
and the flags the change touches are generated on and off.

## Commits

Branches, pull requests, releases and the definition of done: [CONTRIBUTING.md](CONTRIBUTING.md#definition-of-done). A version is raised only by a
release, when the author says so.

Before a commit:

- the repository is public: no names of clients or of their products in code, comments, docs or commits;
- what a text (a doc, a comment, a commit message) says about the code is checked against the code;
- a document in `docs/` has a Russian twin `<name>.ru.md`; a change in one goes into the other, and the
  site lists the twin in `site/config.js`;
- a change a user of the template sees goes into the docs, the README and `docs/roadmap.md` in the same
  pull request.
