# ADR-001: Доменные события проходят три фазы, привязанные к транзакции

**Статус:** принято, 2026-10-03

**Автор:** Владимир Савкин, создатель DotNetSolutionKit

## Контекст

Агрегат поднимает доменное событие, когда с ним что-то произошло: заказ оформлен, баланс исчерпан. Разным
реакциям на одно событие нужны разные моменты:

- **До фиксации записи:** проверить, дополнить связанные данные, положить сообщение в outbox шины. Эти
  действия должны пройти или упасть вместе с записью.
- **После фиксации:** отправить письмо, поставить задачу в очередь, записать что-то ещё. Если запись не
  прошла, их быть не должно, а если упали они сами, запись они уже не отменят.
- **После отката:** компенсировать, очистить кэш, записать в лог, что потеряно.

Обычный путь в .NET - уведомления MediatR, которые публикует сценарий. Тогда момент публикации выбирает
сценарий. Если публиковать до `SaveChanges`, реакция случится, даже когда сохранение упадёт. Если после,
реакция окажется вне транзакции, а сообщение, положенное в outbox в этот момент, пропадёт. Третий
вариант, рассылка из переопределённого `DbContext.SaveChanges`, даёт один момент вместо трёх, и только для
кода, который проходит через это переопределение.

## Решение

Доменные события рассылают перехватчики EF Core, в три фазы, у каждой свой интерфейс обработчика:

| Фаза | Интерфейс | Когда выполняется | Область |
|---|---|---|---|
| Pre-save | `IDomainPreSaveHandler<TEvent>` | внутри `SaveChanges`, до фиксации транзакции | вызывающего: тот же `DbContext`, та же транзакция |
| Post-commit | `IDomainPostCommitHandler<TEvent>` | после успешной фиксации | новая область DI на каждое событие |
| Rollback | `IDomainRollbackHandler<TEvent>` | после отката, с исключением | новая область DI на каждое событие |

События собираются с сущностей, которые реализуют `IHasDomainEvents` (`AggregateRoot`, `EventfulEntity`),
поэтому обычные сущности не несут накладных расходов на события. Перехватчики висят на `DbContext`, так
что конвейер срабатывает при любом сохранении: через репозиторий, через `IUnitOfWork` или напрямую через
контекст.

Конвейер закрывает и то, в чём ошибаются простые варианты:

- **Каскады.** Обработчик pre-save может поднять новые события. Pre-save повторяется, пока новые события
  появляются, до 20 раундов, так что каскад рассылается в том же сохранении и не теряется.
- **Вложенные фиксации.** Обработчик post-commit или rollback, который фиксирует свою транзакцию, не
  рассылает внешние события повторно: рассылка защищена от повторного входа и работает по снимку.
- **Новая область после фиксации.** В этот момент единица работы вызывающего ещё держит завершающуюся
  транзакцию, и её окно outbox закрыто. Новая область даёт обработчику свои контекст, транзакцию и outbox.
- **Работа вне запроса.** Потребители сообщений и задачи Hangfire передают свою область перехватчикам
  (`DomainEventScopeFilter`, `DomainEventJobActivator`). Без этого события, поднятые там, пропали бы.
- **Потеря видна.** События, ожидающие на сущности без области для рассылки, пишутся в лог
  предупреждением и не исчезают молча.

Подробности о каждой фазе и её правилах - в
[Events/Readme.md](../../template/src/common/NamespaceRoot.ProductName.Common.Application/Events/Readme.md).

## Рассмотренные варианты

**Уведомления MediatR.** Отклонены: момент рассылки оставлен каждому сценарию, и ни один момент, который
он может выбрать, не даёт сразу «вместе с записью» и «после записи».

**Рассылка в переопределённом `SaveChanges`.** Отклонена: одна фаза вместо трёх, и только для кода,
который вызывает это переопределение.

**Каждая реакция через шину сообщений.** Отклонена как вариант по умолчанию: реакции внутри сервиса
понадобились бы брокер и потребитель, и выполнялась бы она позже, вне того же вызова. Шина остаётся для
реакций в других сервисах, сообщения в неё публикуются из pre-save через outbox.

## Риски и что с ними делаем

| Риск | Что происходит | Чем закрыт |
|---|---|---|
| Конвейер - наша собственная реализация | Поддерживаем его мы; новичку нужно разобраться в фазах | Тесты диспетчера, каскада, повторного входа и активатора задач в `Common.Tests`; Readme описывает правила каждой фазы. Позже конвейер может уйти в отдельную библиотеку |
| Обработчик post-commit медленный | Запрос, который сохранял, ждёт его: post-commit выполняется синхронно | Правило: всё тяжёлое уходит в задачу, которую ставит обработчик |
| Обработчик post-commit падает | Запись остаётся зафиксированной; реакция теряется | Сбой пишется в лог как ошибка, остальные обработчики всё равно выполняются; реакция, которую нельзя потерять, идёт через outbox в pre-save |
| События, поднятые при сохранении внутри обработчика post-commit | Они не рассылаются: сбор подавлен на время внешней рассылки | Задокументированное ограничение; продолжение, которое рассылает свои события, ставится задачей |
| Код, который сохраняет вне запроса, вне потребителей и задач | Его события пропадают | В лог пишется предупреждение; такой код оборачивает работу в `DomainEventScopeContext.Use(scope)` |
| Один класс реализует два интерфейса фаз для одного события | Его `Handle` выполняется в каждой фазе | Задокументированное ограничение: один класс на фазу |

## Последствия

- Сообщение другому сервису уходит через outbox, только если запись зафиксирована.
- Письмо или задача никогда не уходят для записи, которую откатили.
- Компенсация собрана в одном месте: обработчик rollback получает исключение и события упавшей записи.
- Сценарий поднимает события на агрегате и сохраняет. Когда выполняются реакции, решает не он: это
  задаёт интерфейс обработчика.
- Запросы, потребители и задачи рассылают события через один конвейер, как и тесты на базе в памяти:
  `InMemoryTestExecutionContext` передаёт область в `ActAsync`, см. [ADR-005](005-testing-a-service.md).
