# ADR-004: Версия продукта задаётся вручную

**Статус:** принято, 2026-10-03

**Автор:** Владимир Савкин, создатель DotNetSolutionKit

## Контекст

Сгенерированное решение должно отвечать на два вопроса о том, что запущено: какой это релиз и из какого
кода он собран. Обычный ответ в .NET - библиотека версионирования (Nerdbank.GitVersioning, GitVersion или
MinVer), которая выводит версию из истории git во время сборки. Версия 1 шаблона поставлялась с
Nerdbank.GitVersioning.

Эти библиотеки решают две задачи:

1. **Уникальный номер для каждой сборки.** Он нужен пакету, опубликованному в NuGet: два разных
   содержимых под одним номером ломают всех, кто зависит от пакета. Сервис не публикуется пакетом.
2. **Номер без решения человека.** Номер, выведенный из высоты коммита, ничего не говорит о
   совместимости, а именно ради совместимости читают семантическую версию. Ломает ли изменение
   вызывающего, знает только человек.

Получается, что для сервиса библиотека дублирует то, что уже сообщает коммит, и не даёт того, ради чего
нужна версия. При этом она добавляет зависимость в сборку и требует полной истории git, а CI обычно
клонирует неглубоко.

## Решение

Версия пишется вручную в `version.json` в корне решения, рядом с заметками о релизе:

```json
{
  "version": "1.2.0",
  "releaseNotes": {
    "1.2.0": { "headline": "...", "highlights": ["..."] }
  }
}
```

`Directory.Build.props` читает версию из файла и проставляет её в каждую сборку. Коммит - отдельное
поле: короткий SHA, записанный во время сборки, или `GIT_SHA` из окружения, когда у сборки нет папки
`.git`, как в сборке Docker. `/health` и `/ready` отдают и то и другое вместе с заметками о релизе.

Версия меняется, когда человек решает, что релиз вышел, и тот же коммит объясняет, что в него вошло.
Заметки о релизе всё равно пишут люди; писать их в репозитории, в коммите, который поднимает версию, -
самый короткий путь.

| Вопрос | Где ответ |
|---|---|
| Какой релиз запущен? | `version` в `/health` |
| Из какого кода он собран? | `commit` в `/health` |
| Что изменилось в этом релизе? | `releaseNotes` в `/health` и в `version.json` |
| Что запущено на моей машине? | рабочая копия, которую запускает разработчик |

## Рассмотренные варианты

**Nerdbank.GitVersioning, GitVersion, MinVer.** Отклонены по причинам выше. Схема, которая поднимает
мажорную версию по подвалу `BREAKING CHANGE:` в сообщении коммита, всё равно зависит от человека,
написавшего этот подвал: решение переезжает в сообщения коммитов и никуда не исчезает.

**Коммит внутри версии (`1.2.0+abc1234`).** Отклонено: две сборки одного релиза из разных коммитов
получили бы разные версии, и сравнение версий сравнивало бы коммиты. У коммита своё поле.

## Риски и что с ними делаем

Шаблон не знает, где будет размещено сгенерированное решение и как его будут собирать. Поэтому опереться
он может на процесс команды, а проверки в CI - дополнение для тех, кто их использует.

| Риск | Что происходит | Чем закрыт | Возможная проверка в CI |
|---|---|---|---|
| Версию не подняли | Новый релиз выходит под старым номером; версия расходится с кодом, который она называет | Подъём версии входит в подготовку релиза; ревью релиза проверяет `version.json` | Проверка pull request: код в `src` изменился, а `version.json` нет |
| Подняли не тот уровень: ломающее изменение выходит минорным релизом | Потребители считают, что совместимость сохранилась, например остаются на 1.x, когда код уже 2.0, и ломаются при обновлении | Ревью; [сравнение API](../features/api-diff.md) с `--DiffApi` показывает каждое изменение контракта API | Сравнение API валит pull request при ломающем изменении контракта, пока изменение не объявлено, и объявление истекает со следующей версией. Для поведения, конфигурации и схемы базы данных такой проверки нет |
| Заметки о релизе не соответствуют релизу | Читатели `/health` и заметок получают неверную картину | Заметки лежат в том же файле и в том же коммите, что и версия, поэтому ревью видит и то и другое | нет |

Проверки из последнего столбца - известные варианты, в это решение они не входят. Позже шаблон может
генерировать их, только для GitHub и за флагом.

Второй риск не закрывает и ни одна библиотека версионирования: ни одна не отличает ломающее изменение от
совместимого. Цена ручной версии - дисциплина поднимать её на правильный уровень.

## Последствия

- В сборке нет пакета версионирования, и полная история git не нужна.
- Версия - решение, рядом с которым записана причина.
- Подъём версии, причём на правильный уровень, держится на процессе команды.
- Этот ADR - о версии сгенерированного продукта. Сам шаблон версионируется тегами git; см.
  [версии шаблона](../getting-started/upgrading.md).
