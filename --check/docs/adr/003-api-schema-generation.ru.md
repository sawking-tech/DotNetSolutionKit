# ADR-003: Документ API читается из собранного приложения

**Статус:** принято, 2026-10-03

**Автор:** Владимир Савкин, создатель DotNetSolutionKit

## Контекст

[Сравнение API](../features/api-diff.md) сравнивает документ OpenAPI сервиса по обе стороны pull request,
поэтому ему нужен документ каждого сервиса, полученный в CI без базы данных, без брокера и без секретов,
которых у агента сборки нет.

Все варианты упираются в одно свойство: **чтобы получить документ OpenAPI, надо построить хост.**
Документ берётся из `ApiExplorer`, а он появляется, только когда подключены маршрутизация, соглашения и
фильтры операций. Прочитать его из скомпилированной сборки, не построив приложение, нельзя.

У построения приложения были побочные эффекты. Миграции и начальное заполнение выполняются между
`Build()` и `Run()`, а страж схемы проверяет базу данных при регистрации сервисов, так что вопрос к
сервису о его API трогал базу. Нужно было учесть ещё два факта:

- `WebApplication` сам добавляет middleware аутентификации, как только находит зарегистрированные схемы
  аутентификации. Если убрать его из конвейера, ничего не изменится: обработчики всё равно запрашивают
  незарегистрированные сервисы, и каждый запрос падает. Аутентификация должна остаться вне контейнера.
- Настройки, которые проверяются при старте (ключи API, секреты, публичные URL), проверяются до того,
  как хост что-либо обслужит, а у агента сборки нет ни одной из них.

## Решение

- **Режим только схемы** (`--schema-only` или `SCHEMA_ONLY=1`) собирает сервис без инфраструктуры:
  выключает все переключатели инфраструктуры, не регистрирует ни инфраструктурных сервисов, ни
  аутентификации, ни хранилища секретов и отключает проверку опций при старте.
- **`SchemaHost.Build(args)`** в каждом сервисе строит приложение ровно так же, как `Program`, и на этом
  останавливается. `Program` строит через тот же метод, поэтому документ всегда описывает то приложение,
  которое работает.
- **`SchemaDump.TryWrite`** в `Common.Web` пишет запрошенный документ прямо из собранного контейнера
  (`--dump-schema <file> --document <name>`) и сообщает `Program`, что запуск надо завершить.
- **`scripts/generate-api-schemas.sh`** запускает так каждый сервис и нормализует результат через
  `scripts/normalise_api_schema.py`: иначе окружение в заголовке, версия, URL серверов и окончания строк
  с машины, где собиралась XML-документация, давали бы разницу между двумя одинаковыми контрактами.

## Рассмотренные варианты

Каждый из них пробовали в продукте на шаблоне до этого решения.

**1. Цель сборки, `Microsoft.Extensions.ApiDescription.Server`.** Во время сборки она запускает
скомпилированную сборку сервиса и читает документ из хоста, который та поднимает. На агенте сборки под Linux процесс уже освобождал свой
провайдер сервисов к моменту, когда инструмент запрашивал документ, и сборка падала с
`ObjectDisposedException`. Временем жизни хоста владеет инструмент, поэтому со стороны сервиса это не
исправить.

**2. CLI Swashbuckle, `dotnet swagger tofile`.** Работает без порта: строит хост из класса
`SwaggerHostFactory` в сборке. Но CLI - внешний инструмент, и его среда выполнения должна совпадать со
средой сервиса: версии 9 нужен рантайм .NET 9, так что на .NET 8 она запускается только с
`DOTNET_ROLL_FORWARD=LatestMajor`. Кроме того, каждому сервису нужен для неё класс-фабрика.

**3. Запустить каждый сервис и забрать документ по HTTP.** Нужны порт, ожидание готовности и процесс,
который потом надо убить, и каждый из этих шагов может упасть. Этот вариант упал незаметно: скрипт
останавливал `dotnet run`, а это только запускатель, поэтому сервис оставался на порту; следующий сервис
не мог занять порт, и на запрос отвечал всё ещё работающий. Все документы приходили от первого сервиса, а
прогон сообщал об успехе.

## Риски и что с ними делаем

| Риск | Что происходит | Чем закрыт |
|---|---|---|
| Режим только схемы и настоящий старт расходятся | Документ описывает приложение, которое отличается от работающего | Один `SchemaHost.Build` на оба случая; режим только выключает инфраструктуру и ничего своего не регистрирует |
| Сервис не стартует в режиме только схемы и тихо завершается | Документа нет или он пустой | Сервис завершается с кодом 1 и печатает исключение; скрипт падает, если файла нет или он пуст |
| Новую инфраструктурную зависимость не выключили | Для генерации документа нужна эта зависимость | Её регистрация уходит в слой инфраструктуры, который режим только схемы не регистрирует, или её переключатель добавляется в `SchemaOnlyMode` |
| Свой код вместо инструмента | Поддерживаем его мы | Три небольших класса; каждый вариант выше упал, когда его пробовали |

## Последствия

- Нет порта, ожидания готовности и процесса, который надо убить, поэтому сбои варианта 3 невозможны.
- Для документа не нужны ни инфраструктура, ни секреты, и это совпадает с тем, что есть у агента сборки.
- Документ описывает работающее приложение, потому что `Program` и генератор строят его одинаково.
- Документ одного сервиса получается за секунды.
