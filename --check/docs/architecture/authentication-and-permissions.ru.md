# Аутентификация и права

## Аутентификация

Сервис сам аутентифицирует каждый запрос одной составной схемой:

- JWT из заголовка `Authorization: Bearer` или из cookie с access-токеном, если задан `Jwt:PublicKeyPath`.
  Сервису, который только проверяет токены, нужен открытый ключ; ключ подписи остаётся у сервиса,
  который их выпускает;
- `X-API-Key` для всех остальных запросов: вызовов между сервисами и от самой платформы.

Запрос с токеном уходит в схему JWT, если она настроена, любой другой - в обработчик API-ключа.
[Шлюз](../features/api-gateway.ru.md) пересылает проверенного им пользователя со своим внутренним ключом и
передаёт токен дальше: сервис без `Jwt:PublicKeyPath`, как по умолчанию, принимает запрос по ключу; сервис
с ним проверяет токен ещё раз.

В `Common.Web` есть хелперы, которые ставят и очищают cookie с access- и refresh-токенами.

Сгенерированный сервис регистрирует свой обработчик API-ключа в `Setup/Authentication.cs`:

```csharp
builder.SetupServiceAuthentication<ApiKeyAuthenticationHandler>();
builder.Services.AddAuthorization();
```

## Права

Действие объявляет нужные ему права:

```csharp
[HttpPost]
[RequiredPermissions("orders.create")]
public Task<OrderResponse> Create(CreateOrderRequest request) => service.CreateAsync(request);
```

Глобальный фильтр проверяет их до действия:

| Вызывающий | Ответ |
|---|---|
| анонимный | 401 |
| аутентифицирован, но без какого-то права | 403, problem с перечнем прав |
| аутентифицирован и имеет все права | действие выполняется |
| системный вызов от самой платформы | действие выполняется |

Действие без `[RequiredPermissions]` не проверяется. Swagger показывает права каждой операции.

По умолчанию права берутся из токена: `ClaimsPermissionService` читает claims `permissions`, по одному
claim на право - так JWT разворачивает JSON-массив. Другие сервисы ему не нужны, поэтому он работает и в
решении из одного сервиса. Сервис, у которого права хранятся в другом месте, регистрирует свой
`IPermissionService`.

За [шлюзом](../features/api-gateway.md) токен проверяется один раз, на шлюзе, а сервис получает
пользователя и права в заголовках вместе с внутренним API-ключом; их проверяют тот же фильтр и тот же
`ClaimsPermissionService`.

### Права из отдельного сервиса

Продукт, который хранит права отдельно от токена, ставит `Permissions:Source` в `remote`:

```json
"Permissions": {
  "Source": "remote",
  "Remote": {
    "BaseAddress": "http://permissions:8080/",
    "Path": "/api/v1/permissions/users/{userId}",
    "CacheSeconds": 30
  }
}
```

Тогда `RemotePermissionService` спрашивает у этого сервиса права пользователя - JSON-массив строк - с
внутренним ключом и вызывающим, как при любом [вызове другого сервиса](#вызов-другого-сервиса). Ответ
переиспользуется `CacheSeconds` секунд на пользователя, поэтому отобранное право перестаёт работать в
пределах этого времени.

| Сервис прав | Ответ |
|---|---|
| перечисляет все права, которые нужны действию | действие выполняется |
| пропускает одно | 403 |
| не отвечает или отвечает ошибкой | 503 `PERMISSIONS_UNAVAILABLE`: право у пользователя может быть, и отказ выглядел бы решением |

Системный вызов имеет все права без запроса. `remote` без `BaseAddress` или `Source`, отличный от `claims`
и `remote`, не дают сервису стартовать.

## Токены в cookie

Токен из тела ответа попадает в хранилище фронтенда, где его прочитает любой скрипт на странице. Поэтому
сервис, который выпускает токены, кладёт их в HttpOnly cookie через `AuthCookieExtensions`:

- login отвечает пользователем и его правами, а `IssueTokenCookies` ставит access- и refresh-cookie;
- refresh читает `ReadRefreshTokenCookie`, ротирует оба токена в cookie и отвечает пустым телом;
- logout вызывает `ClearTokenCookies`; ошибка токена тоже очищает обе cookie и отвечает 401.

Access-cookie аутентифицирует каждый запрос, в котором нет заголовка `Authorization`. Тест-правило
сгенерированного сервиса `ResponseContractTests` падает, если действие возвращает тип со свойством
`Token`, `AccessToken`, `RefreshToken`, `IdToken`, `Jwt` или `BearerToken`.

Какой может быть cookie, зависит от того, где работает фронтенд; ограничения соблюдает браузер:

| Фронтенд и API | HTTPS | `AuthCookies` | CSRF |
|---|---|---|---|
| один сайт: один домен или его поддомены; порты не важны | любой | `SameSite: Lax` | браузер не отправляет Lax-cookie в межсайтовых POST; проверка заголовка - второй рубеж |
| разные домены | да | `SameSite: None`, `ServedOverHttps: true` | защищает только проверка заголовка: cookie доходит до межсайтовых запросов |
| разные домены | нет | невозможно: браузер отбрасывает `SameSite=None` без `Secure` | поставить оба за один домен, обратный прокси или [шлюз](../features/api-gateway.md), либо отдавать по HTTPS |

С `SameSite: None` без `ServedOverHttps` сервис не стартует. Так же он не стартует с `None` при
`Cors:AllowedOrigins` `*` и credentials: тогда cookie и заголовок мог бы отправить любой сайт.

С `RequireCsrfHeader` запрос POST, PUT, PATCH или DELETE, который аутентифицировала бы cookie с токеном,
должен нести заголовок `X-CSRF` с любым значением, иначе получает 403 `CSRF_HEADER_MISSING`. Страница с
другого origin не добавит свой заголовок без CORS preflight, а его проходят только разрешённые origin.
Запрос с заголовком `Authorization` или API-ключом не проверяется. Фронтенд отправляет заголовок в
каждом таком запросе:

```ts
fetch(url, { method: "POST", credentials: "include", headers: { "X-CSRF": "1" }, body })
```

В сервисе, сгенерированном из 2.4, секция уже есть в `appsettings.json`, с `Lax` и включённой проверкой.
Без секции, как в решении, сгенерированном раньше, cookie ведут себя по-старому: `SameSite=None` по
HTTPS, `Lax` по HTTP, проверки CSRF нет. Такое решение включает защиту, добавив секцию, когда его
фронтенд начнёт отправлять заголовок.

## Вызов другого сервиса

Клиент, который строит фабрика, типизированный или Refit, становится вызовом другого сервиса продукта
одной строкой:

```csharp
services.AddHttpClient<BillingClient>(c => c.BaseAddress = new Uri(options.BaseUrl))
    .AddInternalServiceHandlers();
```

После этого каждый запрос клиента несёт:

- внутренний API-ключ;
- вызывающего, прочитанного из claims запроса: пользователя, тенанта, роли и права. Вызванный сервис
  проверяет права так же, как заголовки от шлюза. Работа без запроса за спиной, фоновая задача или
  консьюмер, вызывает от имени системы. Анонимный запрос никого не передаёт, поэтому открытый endpoint не
  получает права системы в следующем сервисе;
- [идентификатор корреляции](web-layer.ru.md#корреляция) текущей работы.

Клиенту внешнего провайдера достаточно `.AddCorrelation()`: ключ и данные пользователя провайдеру видеть
не положено.

## Тесты

`Common.Tests` проверяет на тестовом сервере открытое действие, анонимного вызывающего, отсутствующее и
имеющееся право, системный вызов. Для вызова другого сервиса через клиент из фабрики проверяется, что
уходит с запросом от пользователя, от фоновой задачи, от системы и от анонимного запроса.
