# Валидация и пагинация

Невалидный аргумент отклоняется до выполнения действия, с 422 и validation problem, где названы поля:

```json
{
  "title": "One or more validation errors occurred.",
  "status": 422,
  "errors": { "name": ["'Name' must not be empty."] },
  "code": "VALIDATION_ERROR",
  "correlationId": "..."
}
```

Каждая из проверок ниже отвечает так же, поэтому клиент обрабатывает один вид ошибки ввода.

## Валидаторы

Валидаторы - классы FluentValidation в API-сборке сервиса. `AddPlatformWebApi` находит их сканированием,
поэтому существующий валидатор всегда зарегистрирован, а SharpGrip запускает их до действия:

```csharp
public sealed class PlaceOrderValidator : AbstractValidator<PlaceOrderRequest>
{
    public PlaceOrderValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty();
        RuleFor(x => x.Lines).NotNull().Must(lines => lines!.Count > 0);
    }
}
```

Цепочка правил останавливается на первой ошибке, поэтому `NotNull().Must(...)` не разыменовывает только
что отклонённый null и не бросает исключение из валидатора.

Значение, которое не биндится, например текст вместо числа или тело с невалидным JSON, получает такой же
ответ.

## Текст, который читают люди

Поле, которое один человек набирает, а другой читает (имя, комментарий, сообщение), проверяется после
нормализации, чтобы невидимый символ не спрятал разметку от проверки:

```csharp
RuleFor(c => c.Name).MustBeSafeNormalizedText().MustBeWithinNormalizedLength(100);
RuleFor(c => c.Email).MustBeNormalizedEmailAddress();
```

`PlainText.Normalize` обрезает пробелы по краям, применяет нормализацию Unicode и удаляет символы
форматирования: пробелы нулевой ширины, BOM, переопределения направления. `<scr` + пробел нулевой
ширины + `ipt>` не содержит тега, пока что-нибудь не вырежет этот символ, поэтому проверка сырого
значения его пропустила бы. `MustBeSafeText` отклоняет угловые скобки и управляющие символы, кроме
табуляции и переводов строки; правило длины считает то, что будет сохранено. Адрес проверяется как адрес:
`javascript:alert(1)` разметки не содержит, но `MustBeEmailAddress` его всё равно отклоняет.

## Пагинация

Запрос с пагинацией реализует `IPaginationRequest` (`Page`, `PageSize`). До действия проверяется, что
страница не меньше 1, а размер страницы от 1 до 1000 или до лимита, который объявляет тип запроса:

```csharp
[PaginationLimit(200)]
public sealed record ListOrdersRequest(int Page, int PageSize, string? SortBy, SortDirection SortDir)
    : IPaginationRequest, ISortableRequest;
```

OpenAPI-документ указывает те же границы для параметров `page` и `pageSize`. Действие, которое принимает
тип с этими свойствами, но не делает пагинацию, отказывается от проверки через
`[SkipPaginationValidation]`.

Сортировка по полю, которое репозиторий не разрешает, получает 400 со списком разрешённых полей; см.
[хранение](persistence.md).

## Почему 422

Любая проваленная проверка ввода отвечает 422, поэтому у клиента один статус для «исправь ввод». 400
остаётся для запросов, которые отклоняет сам код через `BadRequestException`, например сортировки по
полю, которое endpoint не предлагает.

## Тесты

`Common.Tests` проверяет на тестовом сервере, что проваленный валидатор, выход пагинации за границы и
лимит конкретного запроса отвечают 422 до выполнения действия, что имена полей совпадают с JSON и что
границы в OpenAPI совпадают с проверкой.
