# CI на GitHub Actions

Генерируется с `--GitHubCiCd`, по умолчанию выключено: у каждой команды свой CI, а эти workflow работают
только на GitHub. Флаг передаётся с `--Solution`; workflow покрывают все сервисы в `All.sln`, поэтому
следующему сервису ничего больше не нужно.

## `.github/workflows/ci.yml`

Запускается на каждом пулл-реквесте, на push в `main` или `master` и вручную, с покрытием по запросу:

1. Падает, если проект сервиса отсутствует в `All.sln`. Сервис попадает туда при генерации;
   проект, добавленный вручную и забытый там, выпадет из сборки и из тестов, и ничего не упадёт.
2. Собирает `All.sln` в Release.
3. Запускает юнит-тесты: всё вне категории `TestCategory=Integration` (`[Integration]` в сервисе, `[Category(TestCategories.Integration)]` в `Common`).
4. Запускает интеграционные тесты на реальных серверах, которые поднимает в джобе `tests/servers/up.sh` -
   те же скрипты, что запускает разработчик: PostgreSQL или SQL Server всегда, ClickHouse с `--ClickHouse`,
   MongoDB с `--MongoDB`, MailHog с `--Notify email`, SeaweedFS с `--Storage`, Vault с `--Vault`. Серверы
   стартуют до сборки, а их готовности джоб ждёт перед интеграционными тестами. PostgreSQL держит данные на
   ramdisk с выключенной надёжностью записи; это безопасно только потому, что данные умирают вместе с
   джобом. См. [тестирование](../architecture/testing.md).
5. Если покрытие запрошено, снимает его по обоим прогонам: отчёт по каждому сервису и по `Common`, сводка
   каждого на странице прогона, HTML-отчёты в артефакте. Исключена обвязка без своей логики: миграции,
   конфигурация модели, композиция DI и её расширения, настройка хоста, сидинг, контроллеры - в
   контроллере нет логики - и обработчики и фильтры безопасности, которые покрывают интеграционные тесты.
   В отчёте шлюза его трансформации остаются. Отчёты строятся, даже если какой-то тест упал.

Пулл-реквест покрытие не снимает: при тысячах тестов замер каждой ветки на каждом пулл-реквесте стоит
дороже, чем говорит, а пулл-реквесту нужны тесты на код, который он меняет, и это проверяет ревью.

Покрытие ветвлений валит прогон, если какой-то отчёт ниже переменной репозитория `COVERAGE_MIN_BRANCH`,
в процентах; отчёт совсем без ветвлений, новый сервис, которому ещё нечего решать, порогу не подлежит.
Без переменной отчёты показываются и ничего по ним не падает: команда задаёт порог, когда
тесты появятся, и поднимает его без правки workflow.

## `.github/workflows/coverage.yml`

Запускается руками на ветке, выбранной при запуске: `ci.yml` с покрытием. Показывает покрытие ветки до её
пулл-реквеста. Другой workflow тоже может вызвать `ci.yml` с покрытием (`workflow_call`, вход `coverage`).

## `.github/workflows/secret-scan.yml`

Прогоняет [gitleaks](https://github.com/gitleaks/gitleaks) по коммитам, которые приносит пулл-реквест или
push, с `tools/gitleaks/.gitleaks.toml`: набор правил gitleaks плюс пароли в строках подключения, URI с
учётными данными и ключи подписи в JSON-настройках. Значения с пометкой `test-do-not-use`, `placeholder`
или `changeme` и ссылки `${VARIABLE}` разрешены.

Сканируются только входящие коммиты, поэтому находка в старой истории не валит каждый следующий прогон.
Чтобы один раз просканировать всю историю, например при подключении workflow в существующем репозитории:

```bash
gitleaks detect --config tools/gitleaks/.gitleaks.toml --redact
```
