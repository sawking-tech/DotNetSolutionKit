# Фоновые задачи

Включены по умолчанию; `--Hangfire false` генерирует сервис без них. Задачи работают на Hangfire и
хранятся в СУБД решения, PostgreSQL или SQL Server, в отдельной схеме сервиса (`orders_hangfire`) рядом со схемой сервиса и под той же
защитой.

## Конфигурация

```json
"HangfireSettings": {
  "DashboardUser": "admin",
  "DashboardPassword": "",
  "WorkerCount": 10
}
```

Пароль обязателен и не имеет значения по умолчанию: без него сервис не стартует. Дашборд доступен по
`/hangfire`, за basic-аутентификацией с этими учётными данными.

## Написать и поставить задачу

Задача - класс в инфраструктуре сервиса; она берётся из контейнера в собственном scope:

```csharp
public sealed class ExpireUnpaidOrdersJob(IOrderRepository orders, IUnitOfWork unitOfWork)
{
    public async Task ExecuteAsync()
    {
        // ...
        await unitOfWork.SaveChangesAsync();
    }
}

RecurringJob.AddOrUpdate<ExpireUnpaidOrdersJob>("expire-unpaid-orders", job => job.ExecuteAsync(), Cron.Hourly());
BackgroundJob.Enqueue<ExpireUnpaidOrdersJob>(job => job.ExecuteAsync());
```

Что шаблон добавляет к обычному Hangfire:

- Доменные события работают в задачах. `DomainEventJobActivator` даёт каждой задаче scope, который видят
  интерсепторы доменных событий, поэтому события, поднятые задачей, диспатчатся как в запросе.
- Актор переходит вместе с задачей. `JobActorPropagationFilter` запоминает, кто поставил задачу, и
  восстанавливает этого пользователя на время её работы, поэтому то, что пишет задача, приписывается ему.
  У запуска по расписанию такого пользователя нет, и он работает от имени системы. Задача, которая
  действует от своего имени, даже если её поставил кто-то, берёт контекст из
  `ISystemExecutionContextFactory.Create()`.
- Корреляция переходит с каждой задачей. Тот же фильтр запоминает трейс и
  [идентификатор корреляции](../architecture/web-layer.ru.md#корреляция) работы, которая поставила задачу,
  поэтому строки её лога находятся вместе со строками запроса. Запуск по расписанию начинает собственный
  трейс и коррелируется по нему.
- `/ready` проверяет Hangfire: проверка здоровья падает, когда не запущен ни один сервер Hangfire.

## Почему Hangfire

Из библиотек фоновых задач для .NET она удобнее всего для задач сервиса:

- разовые, отложенные и повторяющиеся задачи через один компактный API, с повторами и историей каждого
  запуска в СУБД решения;
- дашборд из коробки: что выполнилось, что упало и почему, с кнопкой повтора;
- задачи - обычные классы из DI, поэтому тестируются как любой другой класс.

Quartz.NET заметно сложнее поддерживать: та же задача требует больше кода, а дашборда в нём из коробки нет.

Другого способа запускать задачи в шаблоне нет. Там, где Hangfire не подходит, сгенерируйте сервис с
`--Hangfire false` и запускайте фоновые задачи так, как вам удобно (внешний cron или Kubernetes
CronJob, hosted service, отложенные сообщения шины).

## Тесты

Задача только оркестрирует: её тесты мокают порты, которые она вызывает, и проверяют вызовы, а логика,
которую она вызывает, тестируется как сервис. См. [ADR-005](../adr/005-testing-a-service.md).
`Common.Tests` покрывает активатор задач.
